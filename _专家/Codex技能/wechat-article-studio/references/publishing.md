# 排版、封面与发布包

## 正式成果结构

```text
<系列>/公众号文章/
  00_系列选题规划.md
  03_发布手册.md
  发布包_第1篇_短标题/
    长图文发布包/
      正文_第1篇_短标题.html
      01_标题作者摘要.txt
      封面_第1篇_短标题.jpg
    卡片发布包/               # 后台派生卡片文章；用户明确制作时才有
      01_标题作者摘要.txt
      02_卡片正文（纯文本）.txt
      HZYJSJ_孩子与手机_第01篇_卡片_01_封面_v01.jpg
      HZYJSJ_孩子与手机_第01篇_卡片_02_内容_v01.jpg
  _预览/<系列名>_全部正文预览_<N>篇.html
  _build_preview.py
```

手册名称可沿用既有系列，新系列默认使用 `03_发布手册.md`；朋友圈／家长群转发文案写在各篇 `01_标题作者摘要.txt` 第 7 项，不再另建系列级 `04_转发文案.md`。既有 `04_*` 保留。**长图文发布包仅放三件成品**（正文 + 01 字段表 + 封面）；**02 发布操作指南自 2026-09-10 起不再生成新篇**，操作步骤、后台字段说明和发布前自查清单统一写在系列级发布手册里。正式正文只存一份；预览是派生副本。

### 样板目录的生命周期

- Gate 2 只建立最少的 1–2 个 `样板_*` 目录供正文与排版评审，不为全系列批量建立“样板”。样板不是正式交付物，也不能在正式发布包完成后继续充当预览真源。
- 对应正式包组装完成后，先逐文件核对样板与正式正文／字段表；内容应一致的文件用 SHA256 证明一致。随后把 `_build_preview.py` 等调用方切换为读取 `发布包_*/长图文发布包/正文_*.html`，预览文案也必须从“样板”更新为“正式文章”。
- 清理样板前依次完成：列出目录与文件 → 哈希比对 → 全局搜索调用方 → 更新脚本 → 重建合并预览 → 核对文章篇数与顺序。确认无未解决的评审需求后，才按 `maintenance.md` 走回收站。
- 清理后再次全局搜索 `样板_*` 的有效引用并运行全系列自检。除非存在有记录的待评审差异，已完成系列的 `公众号文章/` 下不保留样板目录；正式发布包是唯一内容真源。

新制作后台派生卡片文章时采用两层结构；旧系列三件套直接放在 `发布包_*/` 根目录仍然合法。迁移按“逐篇随做”：只有某篇的 Gate A、Gate B 均通过并开始正式组包时，才把该篇长文三件套移入 `长图文发布包/`，再建立 `卡片发布包/`；不为未制作卡片的篇目批量迁移。磁盘目录沿用 WorkBuddy 及现有工具识别的 `卡片发布包/`，文案与复盘中称“后台派生卡片文章”以避免概念混淆。卡图上传文件名必须按`card-article.md`使用系列资产码实现公众号素材库全局唯一，不能只靠篇号或本地目录区分。既有 `02_*.txt` / `02_*.md` 是历史产物，保留不删、也不反向补齐。

字段表包含标题、作者、摘要、备选标题和必要的后台填写说明，不编造链接；第 7 项放一屏内、第一人称的朋友圈／家长群转发文案，首行能独立呈现，不复述摘要、不使用“必看／码住”等广告腔或索取互动。后台【作者／署名】填账号名“归途有光·和孩子一起重启”，不要填正文叙事者。发布手册写明复制正文、填写字段、上传封面、手机预览和由用户保存／发布的步骤，并引用实际文件名。

## 微信正文规范

- section 管布局，每个布局块使用 `box-sizing:border-box;width:100%`；卡片靠背景、内边距、圆角和边框呈现。多列信息改纵向堆叠。
- 不用 table/tr/td、div、h1–h4、ul/ol/li 布局；不用 class、style 样式块、img 和 data-* 属性。不要设置容器级固定宽或 `max-width` ≥200px，也不用 `align="center"` 嵌套居中。
- p 管正文：默认 `font-size:16px;line-height:1.9;margin:0 0 12px`；卡片文字行高约 1.85。段距使用 margin，不堆空段或双 br。
- 段内可单 br；白字标题一行一个独立 p，禁用 br 拆白字标题。
- 文字色写在实际承载文字的 p/span/b/strong 上，不写在 section 容器上；每个元素仅一个 style 属性。
  - ⛔ **块内不得「裸文本 + 内联元素」混排**（2026-09-21 修正，**取代旧「`<b>` 须声明 `font-size`」——那条已证伪**）。凡 p/section 内既有裸文本、又有 b/strong/span 等内联元素，微信会报「行高小于字体大小，且存在多行文本，可能导致文字重叠」（#2.3.2）。**真根因**：官方用真实浏览器测行框数（`range.getClientRects()`），内联元素边界被算成额外 rect → 行数虚增 → 平均行高被除小 → 误判叠字。**与 font-size / line-height 取值无关**（补字号、写 inherit、调大行高、删行高，全都照样报）。**修法**：块内直接子级的裸文本也用**无样式 `<span>`** 包起来（或让强调独立成段），视觉零变化。工具：`wechat_official_verify.py`（官方真机检测，权威）+ `wx_html_fix.py`（`D:p内混排 N`，启发式筛查）。
  - ⛔ **控嵌套**：不用连续多层「只为了包一层」的 section；把背景+padding+圆角+边框合并到一个 section。官方口径：同 tagName+同内联样式+仅单子节点的连续链 ≤10 层；官方检测器 `nestNodes`（DOM 深度 ≥15）更严。
  - ⛔ **一律不写 `font-family`**（官方第 3 章「不建议设置任何字体族」；公众号已内置优化默认栈，自定义会破坏一致性）。
  ⚠️ **「官方检测通过」≠「符合文档」**：官方规范 22 章节，检测器只覆盖 15 个，**7 个章节完全不查**——唯一「函数已实现但未接入」的是 `font-family`；其余 6 个（`4.2.1 背景容器`/`4.2.2 嵌套关系`/`4.3.1·4.4.1 图片承载纯文本`/`4.3.2 透明底图`/`4.3.3 补色`/`4.5.2 !important`）**连实现都没有**。这些项**事后无法拦截**，只能靠生成阶段写对。`wechat_official_verify.py --list-rules` 可随时查这 7 条。
  - ⛔ **多段共用同一背景时，背景写公共容器**，不给相邻多段各写一份相同 background。
  - ⛔ **其余禁用项**：`line-height` < 字号 / `line-height:0`、`text-align:start|end`、`<pre>`、`height:0`、固定 `height`+`overflow:hidden`+含文字、固定 `width:≥200px`、大 `margin-left`、`position:absolute`/`transform` 破坏视觉顺序、`!important`、渐变背景承载文字、图片承载纯文本。
- 正文、小标题和说明左对齐；大标题、金句、陪伴卡等需要居中的块自行指定 center。
- 固定账号级视觉，不为每个系列发明新颜色。主色优先从莫兰迪紫灰 `#7a6f8f`（深色 `#655b79`）或墨蓝绿 `#3f6f6a` 中选定长期锚点；主题副色限暖琥珀 `#c99a5b`、苔绿 `#6b8f6a`、赤陶棕 `#b06a48` 等既有组合。同一页面强调色不超过两个色系，新色须在 Gate 1 说明并确认。视觉语言保持暖光、近景、留白和日常物件。
- 顺序通常为标题块、故事、台词卡、正文与方法卡、“我后来试的几件小事”、金句、预告／陪伴卡、来源说明。
- 正式正文顶部不生成“上一站／下一站”等前后篇视觉导航：粘贴到公众号后它们不能点击，且会与公众号合集的自动导航重复。系列连续性由统一眉题、内容承接和公众号合集承担。正文结尾可以自然预告下一篇要解决的问题，但不得伪装成按钮、链接或可点击控件；写不出自然承接时直接省略。
  - **分工（2026-09-21 明确）**：**眉题**（`第 N 篇 · 共 M 篇 ｜ 第X季 · 板块名`）＝**唯一**系列坐标提示；**跨篇跳转**＝公众号合集（专辑），平台原生可点击；**整体地图**＝只在总纲/末篇出现。
  - **存量豁免**：2026-09-21 之前生成的系列（如《青春期30讲》17 篇）**保留原样、不追溯修改**；仅对**新生成/点名返工**的正文生效。自检 `--legacy` 模式下不判此项失败。
- 独立分享卡可有适合截图的固定画布；嵌入正文时必须改为上述流式布局，不把卡片截图宽度带入正文。
- **正文内干货卡**与**后台派生卡片文章**不是同一产物。前者仍用 section 流式 HTML；后者使用竖版图片 + 纯文本描述，具体读取 `card-article.md`。不得把后台派生卡片当正文图片插入长文。

## 封面

- 本项目目标：JPG、约 2.35:1、每张不超过 200KB、无装饰文字，核心物件在中央安全区，主题与正文相呼应。
- 默认优先静物与暖光：门、拖鞋、书桌、两瓶水、约定纸等，主体有足够可辨识度，避免缩成远处一条细带。
- 有人物时遵循已确认设定：中年父亲与约 15 岁少年，人数、年龄、构图准确，为横幅留边，不切掉核心人物与道具。
- 先完成可评审的一组封面，获得 Gate 3 明确确认后再批量；同一系列已经完成该 Gate、只是继续复用已批准风格时不重复确认。不得把正文或样板确认外推为封面授权。
- 使用当前生图／编辑工具支持的流程。尊重工具与来源标识规则，不自动去除第三方标记，不复用原专家针对其他平台的固定裁切坐标。
- 逐张检查主题、可读性、比例、大小、裁切。图片缺失或尺寸体积不满足时，写清待完成项。

## 预览与验证

系列两篇及以上提供按篇号排序的单文件合并预览，放在 `_预览/`：篇号导航、上／下一篇、键盘左右键、当前篇高亮和总篇数。正式组包后，预览生成器只读取正式发布包；页面状态用语必须与当前阶段一致，不保留“样板”“封面待制作”等过时提示。只向预览工具打开派生页，保护正式源文件。

项目根目录的工具脚本可复用，运行前先确认参数与范围：

```text
python 工具脚本/系列发布全套自检_selfcheck.py --dir <系列/公众号文章> --source <实际来源关键词>
python 工具脚本/系列发布全套自检_selfcheck.py --dir <系列/公众号文章> --legacy --source <实际来源关键词>
python 工具脚本/微信HTML规范校验修复_wx_html_fix.py --check <正文文件...>
python 工具脚本/wechat_official_verify.py <新生成或点名返工的正文文件.html>
python 工具脚本/wechat_official_verify.py --dir <系列/公众号文章>
python 工具脚本/wechat_official_verify.py --dedupe <正文文件.html> --dry-run   # 冗余嵌套清理预览
python 工具脚本/wechat_official_verify.py --setup                              # 环境探针自检
```

官方检测工具封装了官方**全部三条命令**（`check` 检测 / `dedupe` 清理冗余嵌套 / `probe` 环境探针；官方 README 里的 URL 抓取是规划项、未实现）：

- **`check`**（第 4、5 条）：全规则检测。**每篇新生成或用户点名返工的公众号正文 HTML，在样板交付／正式交付前用第四条逐篇检测一次；检测后若修改正文，对最终文件复检。系列正式交付前再用第五条汇总检测最终发布包。**不自动追溯扫描或返工旧文章，除非用户要求。官方结构检测以 Chromium 实际布局检查行高重叠、过深嵌套、固定宽与暗色模式等，不能代替 Android／iOS 微信客户端预览。
- **`dedupe`**（第 6 条，治 `nestNodes`）：官方清理命令会**真删冗余嵌套层**。⚠️ 它输出的是**正文片段**，会丢 `<html>/<head>/<title>/<body>`，本工具已**自动回填外壳并保留 title**，输出可直接粘贴。已知格式归一（HTML 等价、不影响显示）：`<br>`→`<br/>`、属性引号统一双引号、缩进重排。**安全判据 = 剔除标签后的可见文本逐字一致**（工具逐篇显示 ✅/❌，出现 ❌ 不得写回）。**先跑 `--dry-run` 预览**；确认后去掉该参数才写回，工具会自动备份到 `_备份/dedupe前_<时间戳>/`。
- **`probe`**（第 7 条）：环境探针，验证 puppeteer + 注入 bundle + 全规则（含布局类）跑通。

Windows PowerShell 运行前设 `$env:PYTHONUTF8='1'`，避免中文与符号输出触发 GBK 编码错误。**以报告中的“违规 0 篇｜执行异常 0 篇”为通过判据，不能只看进程退出码**；发现违规则定位、修正并重跑，环境失败则明确报告未完成该项。**首次运行或缓存缺失时该脚本会自动 `git clone`、`npm install` 并下载浏览器依赖**：先检查缓存和脚本行为，涉及安装／联网时按当前执行权限取得批准，不静默触发。缓存或检测环境不可用时报告缺口，不把本地启发式检查称为官方检测通过。即使官方检测通过，也须人工核对检测器**完全不查**的 7 个章节（见生成阶段条款；`--list-rules` 可随时查）。

`wx_html_fix.py` 的“块内混排”是启发式筛查，不是官方判定的等价实现；修复时把与内联元素并列的直接裸文本包进无样式 `<span>`，或把强调独立成段，不靠给 `<b>` 补字号或调大行高掩盖告警。`nestNodes` 与行高重叠是不同规则，按官方报告分别定位。`table转section_微信正文流式重构.py` 和部分预览脚本的 `--fix` 也会写入，只能用于获准修改的范围，事先保留恢复副本。不要把修复命令当检查命令运行。

架构级规则变更（例如从 `table` 迁移为 `section`）后，不能只修改主条款：须横向扫描技能入口、说明文件、相关 references 和工具规范中的正向描述。旧关键词只允许保留在禁用说明、历史迁移记录或工具名中；任何仍把旧方案当作当前做法的表述都必须同步清理。

脚本检查不能代替以下人工核对：

1. 已批准篇数、连续篇号和导航对应；源标题、字段表和手册确实一致。去标点比对仅消除格式差异，不能掩盖漏字。
2. 来源准确；没有无据数据、绝对化承诺或把虚构冒充纪实。
3. 长图文三件套齐全（正文 + 01 字段表 + 封面）；既有系列的 `02_*` 属历史产物、放行不报错；封面真实比例、体积与画面合格。若该篇有后台派生卡片发布包，再按 `card-article.md` 单独核对，不能用长图文三件套规则误判。
4. 正文无禁止元素、固定宽、`font-family` 和污染属性，标签配平；核对块内混排、无意义嵌套、相邻同背景段是否共用容器，以及固定高度裁切、`text-align:start/end`、`line-height:0`、渐变文字背景、`!important` 等新禁用项。手机窄屏检查左右裁切、行距、字色与留白。
5. 合并预览正文篇数正确，不能把导航标签 arttag 当正文容器 art；预览展示后确认正式源文件未被改写。

脚本通过不等于已经在微信安卓／iOS 客户端验证。交付说明分别报告静态检查、实际预览和未验证的客户端表现，不沿用历史“全部通过”作为本次结果。

## 项目产物落位规则（工作空间根目录约束）

工作空间根目录**只允许**：①文章/讲书系列目录 ②系统项（`.git/`、`.gitignore`、`.workbuddy/`）③固定的管理目录。其余一律归位：

| 产物类型 | 落位 |
|---|---|
| 一次性报告/方案/验收记录 | `_档案/报告/` |
| 一次性验证小样、临时实验目录 | `_档案/<名称>/` |
| 专家包与其派生物（`*.zip`、其他平台技能目录） | `_专家/` |
| 各类备份 | `_备份/<对象>/` |
| 长期资产（`真实素材池.md`、`发布数据复盘.md`、`SOP变更日志.md`） | `_资产/` |

`_` 前缀 = 管理类，一眼与内容系列区分。**产物落位要在动手前想好**，不要"先写到根目录、以后再整理"。
