## 2. 核心判断（与 Codex 的两点不同）

1. **先"归位"，后"分层"。** 现在最贵的**不是层级混乱，是同一个事实在 3~4 处各写一遍**
   （典型：时长口径曾在 4 处并存 —— 4.6 字/秒 / ÷4.3 / 不设上限 / 2–4 分钟；**改一处根本不生效**）。
   ⛔ 不先收敛，分层只是把乱摊子换个抽屉。
2. **"历史案例"不是一个层，而是要完全外置。** Codex 说"分四层"，本方案改为
   **三处落位（L1/L2/L3）＋ 一个外置（L4）**。

## 4. ⭐ 两条机制（比分层本身更重要）

### 4.1 Agent ↔ Skill 的分界线：**格式契约的唯一真相源 = Skill**

现在**两边各写了一份"上屏方案怎么写"**——Agent 的「输出规范·各段要点」280 行、Skill 的「文案 MD 怎么写」。
这必然不同步（这正是**硬坑 31「同一条逻辑绝不在两处各写一遍」**，它只管住了代码，没管住文档）。

**划法**：
- **格式契约（字段名/写法/解析规则）→ 归 Skill**（因为**解析器在 Skill 里，代码是最终裁判**）；
- **Agent 侧只留"要写哪几节 ＋ 每节一句意图"**，字段细则**一律指向 Skill**。

### 4.2 每条规则必须能写成**一句可执行判据**

写不出来的（如"要讲清楚""要自然"）：
- 是**原则** → 留 L1，但**浓缩成一句**；
- 是**案例** → 移 L4。

**这是防止文档再次膨胀的唯一闸门**——否则半年后又长回 1100 行。

## 6. 风险与防线

⚠️ **最大风险不是"文档臃肿"，是"规则静默失效"**——搬漏一条判据，比不改危险得多
（同类教训：说明文字静默污染解析、标色跨行静默丢色，都踩过）。

**三道防线**：
1. **可逆**：历史案例**不删**，只移动；每次搬迁前 `git commit` 一次 ✓
2. **逐批复核（用 3.15 的老判据）**：搬完**拿被搬内容的关键词全篇 grep**，看有没有残留/丢失；
3. **功能验证**：搬迁涉及"格式契约"时，**跑一遍 `--preview` ＋ `--dump-params`**，
   确认解析数字与搬前一致（这是唯一能证明"没搬坏"的证据）。

⛔ **不做的事**：不整体重写、不合并文件、不改 Skill 的代码逻辑（只动文档）。
