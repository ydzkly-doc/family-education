## 2026-09-10 · 交付纪律纠正：**「少交付」不等于「少确认」**

**背景**：用户反馈"为什么每次都要执行 present_files，关键是执行这一步很耗时"。Agent 在改进 SOP 时**过度外推**，写成了"消耗额度的步骤可连续推进、不逐篇停问"。

**用户纠正原话**："这个不对，还是要等待我确认，但是可以不用每次都 present_files，需要我会明确给你指令"。

**被推翻的旧做法**：
1. ~~agent md 注意事项原文："…若说直接做/一次做完，记入授权并连续推进，不再逐篇停问"~~ → **删除**
2. ~~Gate 弹性条："用户可显式放行整段流程…按授权连续推进…把确认降级为告知+可回退"~~ → **改为**"关卡本身不可弹性跳过；授权仅限当次点名的那一件事，不得推及未提及关卡"
3. ~~确认判定规则："若用户一次性提前给出跨阶段授权…可视为对相应 Gate 的预先放行"~~ → **改为**"不承认概括式跨阶段授权；判断不了就按未授权处理、停下来问"
4. references/08-selfcheck.md："用 present_files 一次性交付全部成果" → 改为"交付与否听用户指令，不要每步自动 present"

**现行规则（当前唯一正确做法）**：
- **交付维度可松**：present_files 不必每次调用；中间验证/自检/脚本输出不必交付；是否交付、是否打开预览以用户明确指令为准。
- **确认维度绝不放松**：Gate 1/2/3 永远等用户当次、明确、点名到该步的指令。"直接做/一次做完/继续做/接着弄"**不得扩大解释**为对未提及关卡的授权。
- **两者的关系**：**完全无关，不得互相推导**。防抢跑自检表新增第 6 条专门针对此误推。

**附加修正**：references/04-html.md "每次 present_files 之后也应重跑" → "**若打开过 HTML 预览**（预览面板会写回 data-*），交付前须重跑"。

## 2026-09-11 · 封面清晰度：生成用横图、后处理只缩不放

**起因**：用户对比两张封面——Codex 生成的（`孩子摆烂怎么办`第1篇）与我生成的（`青春期30讲`第3篇），指出"清晰、细腻度差异很大"，问有无办法。

**量化结论**（两张均 1200×511，比例一致，故非尺寸问题）：

| 指标 | Codex | 我 | 差异 |
|---|---|---|---|
| 独立色阶数 | 72,488 | 33,832 | **Codex 高 2.1×** |
| 高频细节能量占比 | 3.93% | 2.81% | **Codex 高 40%** |
| 边缘锐度（拉普拉斯方差） | 88.5 | 461.2 | 我高，**但是假象** |

**关键判别**：扁平插画的大色块 + 硬边缘会让拉普拉斯类锐度指标**虚高**（纯色区差值 0、边缘突跳），"锐度高"≠清晰。真实细腻度要看**独立色阶数**与**高频细节能量**。

**查到两个真实原因**：

1. **我方处理链路缺陷（已修）**：旧做法是「生成 `1024x1536` **竖图** → 裁 2.35:1 横带 → **放大**到 1400」。竖图裁横带浪费约 60% 像素，剩下部分再被放大——**两步都在丢细节**。
   - 实测对照（同一源图）：竖图裁带放大到 1400 → 细节保留 **86.1%**；横图裁带缩小到 1200 → **97.6%**。放大 1.37 倍使锐度损失约 **45%**。
   - **修正**：生成一律用**横图**（`1536x1024`）；后处理**只允许缩小、严禁放大**；推荐终稿 **1200×511**（不追求 1400/1536）。
2. **风格差异（待用户定）**：SOP 原文写的是"**扁平治愈插画风**"，这类风格天然像素级细节少。写实摄影（真实材质纹理、浅景深、细颗粒）的色阶数约为其 2.1 倍。**这是风格选择，会改变账号视觉识别**，已写入 `vision.md` 但**明确要求切换前须在 Gate 3 与用户确认**，不单方面替换；存量插画系列不回溯重做。

**落位**：`05-publish-kit.md`（B2 生成用横图 / B3 只缩不放 / B4 正确的细腻度判别）、`vision.md`（写实 vs 插画风格说明 + 需用户确认）

**同步**：cache → marketplace → 重打包 zip；三处归一化比对**完全一致**；`validate_expert.py` ✅ 通过。

## 2026-09-11 · 新增「过程文件定时过期」机制（治本）

**问题本质**：SOP 第 10 步原本只有"用户说清理时才走"的**被动流程**，**缺少"按时间自动判废"的规则**——靠人记着清不现实。

**方案：按"可重建性"分级设保留期**

| 类 | 内容 | 默认保留 | 理由 |
|---|---|---|---|
| **A** | `_预览/` 合并预览页等 | **7 天** | 脚本随时重建，零损失 |
| **B** | `_backup*` / `_备份/` 修复前快照 | **14 天** | 对应修复验证通过后即失效 |
| **C** | `_封面候选/` `_过程文件/` `_未采用*/` `_原始*/` `_归档*/` | **90 天** | 含可复用提示词与参数，不宜过快删 |
| **D** | `_档案/` `_资产/` | **不过期** | 报告与长期资产 |

**配套工具（新增）**：`工具脚本/过程文件过期扫描_scan_stale.py`
- **只读，绝不删除**；按类输出"保留 x/y 天"或"**超期**"，汇总可回收体积
- `--out <路径>` 出 markdown 报告；`--list A` 列某类完整路径供圈选；`--keep-days A=7,B=14,C=30` 覆盖
- 首次扫描结果：**53 个目录 / 52.0 MB，超期 0 个**（现存都是 1–9 天内的新产物）

**节奏**：建议每 1–2 周跑一次（或用户说"清理"时先跑）。**A/B 类超期可批清；C 类超期先人工确认复用价值**（候选图带提示词，删前可摘进该系列手册）。删除仍受 P0 约束：只走回收站 + 分批 ≤10 + 逐批核对 + 清后复检，清前先 `git commit` 可回滚。
