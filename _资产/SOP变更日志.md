## 2026-09-22（二）工具脚本验收纪律：大段替换后必做静态体检

### 事故：替换边界吞掉函数 → 检测路径 NameError
用**两行注释**（`#---- dedupe` 到 `#---- CLI`）作为替换边界重写代码段，
而 `report()` 函数**正好夹在这两个标记之间**，被整段删掉，
但 `main()` 里仍保留 `report(result, args)` 调用 → **默认检测路径抛 `NameError`**。

### 为什么三次手工测试全部"通过"（核心教训）
当时测了 `--setup`、`--dry-run`、`--list-rules` 三条路径，
但**这三条都在到达 `report` 之前就 return 了**——**只有最长路径（默认检测）会走到它**。
**"跑通几条命令"不等于"代码完整"。**

### 新纪律（已写入 `10-ops.md`）
1. **改完 `工具脚本/*.py` 必跑 `python 工具脚本/py_ast_health.py`，退出码必须为 0。**
   该工具用 AST 找「被调用但未定义」的名字，正是"边界吞函数"这类隐患的检测器。
   已用**已知有 bug 的版本反向验证它有效**（精准报出 `L613 report() ← 未定义`，退出码 1）。
2. **测试必须覆盖每条分支**，不能只跑最短路径。
3. **用注释当替换边界时，边界内内容必须先打印并逐项确认**（打印了不比对 = 没看）。
4. 改动写入后**至少真跑一次"最长路径"**（默认检测 / 实际写回），再看退出码。

### 同批修复的另一处
`--dedupe` 的**写回保护**：原先只判断 `ok and not dry_run`，
若官方 clean 意外改变可见文本仍会写回。现改为 **`not e["same_text"]` 时一律不写回**，
并在报告里区分「未写回：文本变化」与「处理失败」两种状态。
已做**分支级验证**（monkeypatch 注入会改文本的 cleaned）：
- 文本一致 → `written='ok'`，磁盘被改 ✅（符合预期）
- 文本变化 → `written=None`，**磁盘未被改** ✅（保护生效）

### 当日另一条操作铁律（已入用户级记忆）
**绝不用内联 `python -c "..."` 写含反引号 / `$()` 的中文文本**——
shell 会先做命令替换，导致①写入失败 ②整段 markdown 被当命令执行 ③内容污染。
当日因此踩第 3 次（前有误触发 `git clone` 事故）。
→ **可靠手法：先用 Write 工具写一个 `.py`，脚本内读入内容再写目标文件。**

- 已知格式归一（HTML 等价、不影响显示）：`<br>`→`<br/>`、属性引号统一双引号、缩进重排。
- 实测（《你是孩子最好的玩具·第1篇》，21,012 → 20,712 字节）：
  `nestNodes 4 → 0`，`isValid False → True`，**可见文本逐字未变**，section 75 → 71（删掉的 4 层全是
  `box-sizing;width:100%;display:block` 纯包裹层，无实际样式）。
- **安全判据定为「剔除标签后的可见文本逐字一致」**（而非嵌套数——嵌套数需 puppeteer 复测且受上下文影响）。
- 写回前自动备份到 `_备份/dedupe前_<时间戳>/`；`--dry-run` 可只预览。

### ③ `probe` 实测
`probe` 用**故意违规的探针 HTML**（透明 `caret-color` + `height-nodisplay` 溢出）验证
「puppeteer launch + 注入 bundle + 全规则（含布局类）」是否跑通。实测通过（4/4）。已接到 `--setup`。

## 2026-09-21（五）行高告警真根因修正 + 生成阶段规则前置化 + 官方检测工具接入

### 背景
用户反馈正文粘贴到公众号后台报「行高小于字体大小，且存在多行文本，可能导致文字重叠」（#2.3.2）。
本次先是**误判根因、白改 41 篇**，后经官方规范 + 官方检测工具实测才锁定真因。

### ① ⛔ 推翻的错误规则（重要）
- **旧规则**：「`<b style>` 必须同时声明 `font-size`」，根因写作「微信把继承来的 `line-height`（如 `1.9`）
  的字面数值与字号比较，`1.9 < 14` 判违规」；修法「补父级字号 + 倍数换算 px」。
- **证伪方式**：官方检测工具（puppeteer 真机）消融实验——补 `font-size`、写 `inherit`、
  调大行高、甚至**删掉行高**，**全都照样报**。
- **代价**：曾据此白改 41 篇（275 处），全部回滚。

### ② 真根因（官方检测器源码 + 真机实测确证）
`<p>`/`<section>` 内**「裸文本 + 内联元素」混排** → 官方按真实布局测量：
`lineCount = range.getClientRects().length`，内联元素边界被算成**额外 rect** → 行数虚增 →
`contentHeight/lineCount` 被除小 → `avg < fontSize × 0.95` → **误判叠字**（视觉实际无重叠）。
**与 `font-size`/`line-height` 取值完全无关。**
→ **正解**：块内**直接子级的裸文本也用无样式 `<span>` 包起来**（视觉零变化）。
→ 工具检查项由 `D:b缺字号 N` 改为 **`D:p内混排 N`**。

### ③ 新发现的独立规则：`nestNodes`（此前被混淆）
官方检测结果**按规则名分组**，`line-height`（#2.3.2）与 `nestNodes`（#2.1 嵌套层级）**互不相干**。
曾把 `nestNodes` 残留误当成「行高没修净」而白追一轮。
`nestNodes` 判定：DOM `data-nest-level ≥ 15`；官方文档口径更宽（同 tagName + 同内联样式 +
仅单子节点的连续链 ≤10 层）。
**存量未处理**：`你是孩子最好的玩具` 系列 7 篇（用户决定暂缓）。

### 2026-09-21 · 新增 D 规则：`<b style>` 必须声明 font-size（微信"行高小于字体大小"告警）

> **来源**：用户粘贴《手机方案·第2篇》正文到公众号后台，微信报 4 处
> 「行高小于字体大小，且存在多行文本，可能导致文字重叠」（参考文档 #2.3.2 line-height-overlapping）。

**根因（实测确认）**：
- 报错 4 段（第 9/23/24/25 段）与「**含 `<b style=…>` 的 4 段**」两个集合**完全相等**
  （`{9,23,24,25}`）；同文件第 21 段也含 `<b>` 但未写 style，**不报** → 触发条件锁定为"**`<b>` 带 style 但不带 font-size**"。
- 机制：微信检测器把**继承来的 `line-height`（无单位倍数，如 `1.9`）的**字面数值**与字号比较，
  `1.9 < 14` → 判"行高小于字体大小"。**技术上不是真重叠，是检测器误报**，
  但告警会挡住发布流程，必须消除。
- ⛔ **写 `line-height:inherit` 救不了**：继承到的仍是 `1.9` 这个数字，告警照旧。
  → 必须把倍数按父级字号**换算成 px 写死**。

**新规则（D 规则）**：
```
❌ <b style="color:#3f6f6a">要点</b>
✅ <b style="color:#3f6f6a;font-size:16px;line-height:30.4px">要点</b>
   （font-size 复制父级；line-height = 倍数 × 字号）
```
- 视觉零变化，仅把数值写明确，让检测器有可比对象。
- **工具已支持**：`微信HTML规范校验修复_wx_html_fix.py` 新增 `D:b缺字号 N` 体检项 + 自动修复
  （无参运行即修，幂等）。已实测：修复前报错 → 修复 → 合格。

**存量修复（用户授权"修复全部"）**：
- 实际范围 **41 篇 / 275 处**（我先报 33 篇是匹配式写错的低估；精确扫描后修正为 41 篇）。
- 备份：`_备份/bfont修复前_20260921_191217/`（41 篇原文件）。
- **复验四项全过**：①残留缺字号 `<b>` = 0；②**正文纯文本零变化**；③标签配平一致；
  ④除 style 属性外无任何其他改动。
- 全库 156 篇正文 `wx_html_fix --check` → **合格 156/156**；20/20 系列全套自检通过。

**⭐ 方法论收获（可推广）**：
1. **定位"报错样本"要靠"集合相等"验证，不是靠猜**：我先猜"长段落易报错"，被数据推翻
   （最长的 8 段全部正常）；改用"报错集合 vs 特征集合"比对，一次锁定。
2. **检测器报"重叠"不等于真重叠** —— 先判断是"真实渲染问题"还是"检测器按数值误判"，
   两者修法完全不同（前者改版式，后者补声明）。
3. **加检测规则时必须做成"可断言 + 可自动修复"**，否则下次仍会漏到发布环节
   （本次问题正是**工具链盲区**：旧版 `wx_html_fix` 根本没有这条检查）。

### 2026-09-21 · 清理流程三条补强（git 兜底的适用前提 / 逐文件降级 / 清后自检预期副作用）

> **来源**：执行一次实际清理（30 项 / 108.3 MB）时踩到的三个新坑，均为既有流程未覆盖的。

   未跟踪时**回收站是唯一退路**，清单留档从"建议"升为"必需"。
2. **`send2trash` 失败要分"假报错 / 部分删除 / 真失败"三种**（原先只写了"假报错"）：

   - **部分删除**：内容已进回收站、留空骨架 + 个别残留 → **重试一次即可收口**（实测留 2 个 jpg）。
   - 另记：运行环境常缺 `send2trash`/`pywin32`，须用隔离 venv。
3. **清后自检存在"预期副作用"，此前未写明易误判**：清理 A 类 `_预览/` 后，

   **否则会把预期副作用误判为"清理弄坏了正式成果"，走错排查方向。**

### 2026-09-21 · 扫描脚本修 bug：判龄一律看「文件真实修改时间」，快照总目录逐项判龄

> **来源**：用户指出「不要看目录时间，看文件真实最后修改时间」。

- **原 bug**：`_备份/` 这类**快照总目录**被按**整体**判龄，而整体取的是"内部最新文件"→
  **往里丢一个新快照，整个容器就变年轻**，把内部早已超期的快照**全部藏住**。
  实测：容器报 **1 天**，内部 **17/34 项已 7–19 天（99.1 MB）**。→ 上一轮报"B 类超期 0"是假象。
- **修法**：
  1. **判龄口径显式化并写入脚本 docstring**：**只看文件 `st_mtime`，目录自身时间一概不看**
     （目录 mtime 因子项增删被改写，不代表内容新旧）。`stat_dir()` 改为返回 `(size, cnt, newest, oldest)`，
     新增 `stat_file()` / `stat_any()` 统一文件与目录入口；空目录按"未知"处理而非 epoch 误判。
  2. **快照总目录逐项判龄**：新增 `is_snapshot_catalog()`（名称以 `_备份` 开头，或含 ≥2 个带
     「公众号文章」层级的子目录）→ 命中则**逐个快照单独算龄**，报告中**逐快照展开成一行**，
     `--brief` / `--list` 也逐条列出。**改判据前实测过 5 种区分规则**，"非过程子目录数≥2"会误报 16 个
     （把 `_过程文件` 的 `卡片成品_待验收`/`封面样板_Gate3` 等阶段目录也算成快照），故弃用。
- **效果**：`超期 12 个 / 7.9 MB` → **`超期 29 个 / 107.1 MB`**，被藏住的 17 个快照全部现形。
- **回归验证**：①57 个普通目录判龄与手工独立实现**逐一致**；②`--keep-days` 覆盖仍生效；
  ③脚本仍**无任何删除/移动/改名调用**（`--out` 写入除外）。
- **可推广教训**：**凡"内含多个独立条目"的目录，判龄必须下沉到条目层，不能用整体聚合值**——
  用 `max()` 聚合会让"新条目"代表"老内容"，是**静默漏报**的典型来源。
- **同步落点**：脚本本体 + 标准版 `10-ops.md` + 派生版 `references/maintenance.md` + 专家包 zip（归一化 0 差异）。

### 2026-09-16 · 卡片文章“过空”修正：一屏一意不等于一屏一句

> **来源**：《儿童情绪管理》5 篇后台派生卡片文章首轮成品。用户连续指出：人物底图容易与正文时间线冲突；第一张也不宜用人物；中间卡文字太少，整体显空。

**问题根因**：执行时把“一屏一意”误做成“一屏一句”，只保证了卡片主题单一，却没有保证单卡信息自足；同时把长文封面的“人物主题”惯性带入卡片文章，额外制造了年龄、关系与故事时点暗示。

**现行规则**：

1. 中间内容卡默认采用“1 个核心判断 + 2–4 个解释点／步骤／边界／可照念台词”，通常形成 3–4 个信息块；只放一句金句或小段摘要视为过薄。
2. 正文建议占可用内容区约 45%–65%。低于约 40% 先回到长文补足信息，不靠空行、拉大段距、同义重复或无据结论填充；高于约 70% 则删减或拆解，不以缩小字号硬塞。
3. 本家庭教育项目的卡片文章默认无人物、弱时间线：封面卡与收尾卡可用静物，但文字安全区保持干净；中间卡使用纯色或轻微渐变。确需人物时在 Gate B 单独确认。
4. 验收按“原尺寸密集卡 → 逐篇预览 → 全系列合并预览”三层进行；缩略图不能替代原尺寸字距、截断与可读性检查。

**本次实证**：15 张中间卡扩充后，均形成 3–4 个信息块；25 张正式卡保持 1242×1656、单张低于 100KB，五篇描述 204–239 字，全套自检通过。

**落位**：Codex 派生版 `references/card-article.md`；WorkBuddy 标准版 `14-card-writing.md`、`15-card-visual.md`，并在 `13-card-article.md` 增加检查入口。

### 2026-09-14 · 【学习工坊首次反哺】7 条全部采纳（用户逐条确认）

> **来源**：公众号学习工坊（wechat-learning-studio）拆解 2 篇外部好文章后编制的 Gate C 反哺清单。
> **样本**：`我的女儿，初二，不去上学了`（36氪/后浪研究所，非虚构特稿，证据：多平台转载≥5处）、
> `为人父母，懂得"闭嘴"才是最高层次的智慧`（女儿派，观点文，证据：多平台转载≥4处+头部账号+被洗稿）。
> **确认方式**：用户明确回复"全部采纳"（Gate C 逐条放行）。
> **写入位置**：`references/02-writing.md`（第 1–7 条）+ `agents/wechat-article-studio.md`（索引与漏读点提醒）。
> **备份**：`_备份/专家包/学习工坊反哺前_20260914/`。

**① 五层完整性按文章类型分轨（最重要，含冲突裁决）**
- **旧值**：五层（场景/心理转折/机制/方法/边界）作为**所有文章**的通用必备标准，"缺一不可；答不全说明删多了"。
- **冲突**：外部样本 #1 **通篇无机制、无方法**，却成为被多平台转载的高传播内容。若按旧标准执行，这类"不给答案"的文章在本体系里永远写不出来。
- **新值**：分轨——
  - **方法文/概念解释文**（清单工具型、读书概念解释型、问题复盘型）：**五层齐全，缺一不可**（不变）。
  - **叙事文**（现场故事型、对话拆解型、一封信/自问自答型）：**必须有场景、心理转折、边界三层，机制/方法中至少写好一层**（允许缺）；验收改用**叙事文三条替代标准**：①细节的诚实度（写"不体面的真实反应"而非"正确的情感"）②情绪的克制度（不给廉价出口/不制造羞耻恐慌）③不确定的承认（不给完满结局）。
- **硬边界**：**"允许缺方法" ≠ "可以不写边界"**。涉及厌学/自伤/抑郁等议题时，专业求助边界照样必须写。
- **同步改动**：自查顺序句改为"先保五层齐全（并按文章类型判断哪几层必需）→ 再压重复句"。

**② 并列式分论点不得同质（新增硬检查）**
- **实证反例**：某爆款文四小标题"当孩子专注时/想尝试时/犯错时/想倾诉时，请闭嘴"——**看着像四个角度，去掉场景差异后核心动作完全相同（减少父母语言输出）**；读者读完觉得"说得很顺"却说不出一条具体做法。
- **新值**：**写完并列式结构必须做"核心动作提取"——把每个分论点的核心动作写成一句话比对，同质则合并或换角度重写。** 理由：同质并列读起来非常顺畅、极易过稿，但制造的是"干货感"而非干货，且是模板感的典型来源。

**③ 小标题拟法（新增，两种轮换）**
- **进程式**（推荐用于叙事文）：每个 2–4 字、用动词/状态词、连起来构成心理进程线（实证范例："**拉扯 → 停学 → 解除烙印**"）。
- **场景锚定式**（观点文可用，须改造）：用"当孩子____时"锚定场景，**但必须去命令感**——不用"请闭嘴"，改为"他写作业的时候，我总忍不住说两句"；副标题不用"别让…变成…"恐吓句，改"后来我才发现…"。

**④ 开头可用"旁观者视角"（新增，与第一人称轮换）**
- **实证范例**："在小面馆吃早餐，旁边坐着一对母子。从孩子吃第一口面条开始，这个妈妈的嘴就像电动小马达一样……"
- **新值**：默认第一人称，但**连续多篇用第一人称会形成模板感**，可轮换旁观视角。要点：交代"我为什么在那儿"；**只写看见的不写猜测的**；给一个动作收尾；**旁观对象最好是陌生人**（不写熟人、不借旁观嘲笑那位家长——那会制造新的羞耻）。

**⑤ 形容词 → 具体事项罗列（新增技法）**
- **实证范例**：不写"妈妈很唠叨"，写"从上课要积极举手、到吃饭不要挑食、从作业要检查、到课间要多喝水……甚至连削铅笔这样的小事，妈妈都要叮嘱一遍"。
- **新值**：**形容词是作者的结论，罗列是读者的体验。** 要点：≥4–6 项；**安排一个"小题大做"的收尾项**（"削铅笔"）制造落差；紧跟一个动作反应（没有后果的罗列只是清单）。**用于自我暴露，不用于指责他人**；罗列不能太整齐。

**⑥ 叙事文收尾：承认不确定，不给完满结局（新增）**
- **实证范例**："未来我的想法会不会改变我不知道……将来我们一起出去摆个摊儿，卖点东西，一日三顿总还是有吧？"
- **旧值**：结尾以"祝愿式收口"为主。
- **新值**：**完满结局对同样处境的读者是不可信的**——承认"不知道"反而让读者觉得"你在跟我说话"。写法：不写"我们已经好了"写"现在我们是这样"；保留一个未解决的问题；给一个微小的可确认变化。**两条硬边界**：不能变成"丧"（必须有微小正向锚点）；**不适用于方法文**；不得以"承认不确定"规避必须写的边界。
- **同时新增**："他人提问—自己回答"收尾法（直接说结论=说教，被追问后回答=坦白）。

**⑦ 正文禁例三条（新增·外部爆款反面样例）**
以下三条**在传播上有效**，但代价与账号立身之本冲突，**一律不写**：
1. **绝对化归因 + 制造羞耻**：反例"想成就孩子，还是毁掉孩子，全看父母的嘴""消极暗示就像一个'诅咒'"。**违反账号锚点"减少羞耻"** + 归因单一化 + 恐吓式驱动。
2. **密集引用不标出处**：反例——一篇引 6 处以上（蒙台梭利/曾奇峰/朱自清/龙应台等），文末零标注，且**多为转述而非原话**（用引号包裹转述有事实风险）。**违反"核不到来源不写"（P0）**。
3. **结尾居高临下的指导姿态**：反例"亲爱的爸爸妈妈们：'嘘，别说话！'"。**与"人设=同路人非导师"根本冲突** + 违反"陪伴卡无动作指令"。
- 每条**均附替代写法**（见正文禁例段）。

## 2026-09-11 · 封面清晰度：生成用横图、后处理只缩不放

**起因**：用户对比两张封面——Codex 生成的（`孩子摆烂怎么办`第1篇）与我生成的（`青春期30讲`第3篇），指出"清晰、细腻度差异很大"，问有无办法。

|---|---|---|---|
| 独立色阶数 | 72,488 | 33,832 | **Codex 高 2.1×** |
| 高频细节能量占比 | 3.93% | 2.81% | **Codex 高 40%** |
| 边缘锐度（拉普拉斯方差） | 88.5 | 461.2 | 我高，**但是假象** |

**关键判别**：扁平插画的大色块 + 硬边缘会让拉普拉斯类锐度指标**虚高**（纯色区差值 0、边缘突跳），"锐度高"≠清晰。真实细腻度要看**独立色阶数**与**高频细节能量**。

**查到两个真实原因**：

1. **我方处理链路缺陷（已修）**：旧做法是「生成 `1024x1536` **竖图** → 裁 2.35:1 横带 → **放大**到 1400」。竖图裁横带浪费约 60% 像素，剩下部分再被放大——**两步都在丢细节**。

   - **修正**：生成一律用**横图**（`1536x1024`）；后处理**只允许缩小、严禁放大**；推荐终稿 **1200×511**（不追求 1400/1536）。
2. **风格差异（待用户定）**：SOP 原文写的是"**扁平治愈插画风**"，这类风格天然像素级细节少。写实摄影（真实材质纹理、浅景深、细颗粒）的色阶数约为其 2.1 倍。**这是风格选择，会改变账号视觉识别**，已写入 `vision.md` 但**明确要求切换前须在 Gate 3 与用户确认**，不单方面替换；存量插画系列不回溯重做。

## 2026-09-15（补）· 新增规则：描述末段必须「自然引导原文」

**起因**：用户要求「卡片正文最后要比较自然地引导用户查看原文」。

### 规则内容

| 项 | 规定 |
|---|---|
| **必须引导** | 描述**末段**要指向长文，让读者知道"完整的东西在那边" |
| **必须自然** | 用**内容指向**（陈述），不用**动作指令**（祈使） |
| **给具体理由** | 说清**长文里有什么是这里没给的**（原样抄的那张纸 / 完整的信 / 全部四步） |
| **位置** | 正文末段（话题标签行的上一段），不单独成行、不加重语气 |

### ⛔ 边界（最容易搞错的一点）

项目既有红线是「**不加动作指令**」。**引导原文也必须遵守这条**——
它和"引流"不矛盾：**用"我留在了长文里"（陈述句指路），不用"点原文看"（祈使句命令）。**

| ✅ 可用（内容指向） | ⛔ 禁用（动作指令） |
|---|---|
| "那张纸我原样抄进了长文" | "点击阅读原文查看" |
| "那三封信我一字不改地留在了长文里" | "想看完整版请点原文链接" |
| "如果你也在等一个'还没变'的孩子——长文里有我贴冰箱的那张纸" | "戳这里看详情" |

## 2026-09-16（账号锚点级）· 「收口双句」不得删：去模板化 = 换表达 ≠ 删该层

**起因**：用户贴出第 12 篇文末的两行——

> 我也是个还在重启的爸爸，立过的规矩也夭折过。

并指出：**「内容比较契合公众号的主题，不要为了去模板化而省略，可以考虑换一下表达方式，尽量保留。
我看有些文章里面没有了。」**

### 🔴 根因：两条 SOP 规则打架，执行时把"换表达"做成了"删除"

| 规则 | 原文 | 被怎么执行 |
|---|---|---|
| 「打破模板感」 | 统计出"**愿你……**式结尾约占 30 篇属实高频"，要求轮换 | 被推广成"收尾句要少用/可省" |
| 「不强制装配件」 | 明确列了"**金句块 / 三件事 / 系列地图 / 下篇预告**"是**可选零件** | **这两句被归进了"可选零件"**，然后按"去模板化"删掉 |

**后果（实测数据）**：**140 篇正式正文中，33 篇缺「身份自述」**——
**王金海讲书 27 篇**（刻意练习 5/5、幸福的方法 6/6、微习惯 5/5 **全缺**；解码青春期 7/8、你是孩子最好的玩具 4/7）
+ **为什么学生不喜欢上学 6/7**。

### ⭐ 判定：**用户的判断成立，且这是账号锚点级内容，不是风格偏好**

| 理由 | 说明 |
|---|---|
| 1 | **读者关注的是"一个爸爸怎么一步步走过来"，不是"这本书讲了啥"**——这两句正是那条主线的落点 |
| 2 | **身份自述**建立**同路人感**，是账号与"专家号"的根本区别（克制说教、减少羞耻） |
| 3 | **认知转折**是**五层中「父母心理/认知转折」层的收口呈现**——**删掉它＝抽掉了那一层的落点**，而"心理转折"是完整性红线的五层之一 |

**→ 结论：把它当"可选零件"删除，是**规则归类错误**，不是风格取舍。**

### 修正后的规则（写入 `02-writing.md`）

**⛔⛔ 收口双句（身份自述 + 认知转折）：账号锚点级内容，必须保留。**

**核心原则**：
> **去模板化 = 换表达 ≠ 删该层。**

**四维轮换表**（这才是去模板化的正确做法）：

| 维度 | 做法 |
|---|---|
| **身份落点** | **每篇换一个具象的"我犯过的那个错"**（"也骂过题海战术""也给孩子递过无数次手机换清静"） |
| **身份称谓** | "重启的爸爸 / 还在学着放手的爸爸 / 不是专家，只是比昨天多懂一点" |
| **转折句式** | "我后来才明白 / 我这才信了 / 后来我算是明白了"——**相邻两篇不得同句式** |
| **转折落点** | 本篇最想留给读者的那一个认知 |

**边界（哪些才算"真的不能写"）**：仅当本篇主题确与"我的转变"无关（纯工具/速览/合集类），可**缩短为一句**，
**但仍须保留身份落点**——**不得整块消失**。

**位置**：文末、来源声明之前；两句一组，不单独加粗、不加重语气。

### 新增工具：`工具脚本/收口双句巡检_check_closing.py`

三档判定，避免"误报一片"：
- **strong**：有"我的认知变化"（转折标记 + 认知动词）——最理想
- **weak**：有"认知落点"（认知对照句 / 收束式结论）——也认可，但标"弱"供人工判断
- **缺**：真没有

同时报 **相邻篇句式重复**。用法：`python 工具脚本/收口双句巡检_check_closing.py <系列目录>`（或 `--all`）

   按换行切会得到 1 段、**整篇被误判为"全缺"**（孩子不上学了怎么办 6 篇即此误报）。→ 改为**按块级闭合标签切分**。

3. **两个 bug 都是"脚本说得太绝对"**——**工具的数字也要能对得上实际**（呼应 09-15 字数口径那次教训）。

| 版本 | 写法 | 结果 |

| **4** | `ImageDraw` → `Image` → `list(im.getdata())` | ✅ 简单可靠 |

## 2026-09-17 · 卡片张数规则修正：**由内容厚度决定，不固定 2+3**

**用户指令原文**：
> 「制作卡片文章中我建议卡片数量是2+3，3张内容卡只是我的建议，你要根据原始内容的厚度给出你建议的张数，不要机械的执行2+3」

### 问题诊断（改前）

SOP 里"封面 1 + 内容 3 + 收尾 1 = **共 5 张**"被写成**多处命令式默认**，
且**只有"上限是几"、没有"该用几"的判定方法**：

| 位置 | 改前表述 | 问题 |
|---|---|---|
| `14-card-writing.md` 1.0 | 「**本工坊默认** 共 5 张」 | 写成"默认"，暗示每篇都该是 5 张 |
| 同上 1.2 | 「为什么内容卡**只要 3 张**」 | 只解释"3 张够用"，未说"1–2 张也可以" |
| `13-card-article.md` 工作流 | 「按"一屏一段"设计 **5 张**」/「渲染 **5 张卡**」 | **命令式**，直接指示执行 5 张 |
| `13-card-article.md` 检查清单 | 「张数 **≤5**」 | 只给上限，无依据要求 |
| `14-card-writing.md` 2.3 | 「张数**收敛到 5 张**」 | 把 5 张当收敛目标 |
| 本体 / README / `10-ops` / `15-visual` | 「共 5 张」「含 5 张」「上传 5 张卡」「单篇 5 张预览」 | 固定值散落多处 |

**→ 后果**：易导致两个方向的机械执行——
① 把 1 个意思**拆成 2 张凑数**（空卡、注水）；
② 把 3 个独立意思**硬塞进 1 张**（过载，读者读不完就滑走）。

### 修正核心：**张数是「果」，不是「因」**

**新增判定法**（`14-card-writing.md` 1.3）：

1. **数意思单元**——通读长文，标出**互不重复、能独立成立**的核心意思
   （一条判断 + 它的支撑：为什么/怎么做/边界/台词）。
2. **一个意思单元 = 一张内容卡**（卡内承载 2–4 个支撑块）。
3. **意思单元 ≥4 → 先合并同类**（用 `quad`/`compare`/`timeline` 并进一张），不是加卡。

| 长文核心意思数 | 内容卡 | 总张数 | 适用情形 |
|---|---|---|---|
| **1** | 1 | **3** | 只讲透一件事（**平台实测最优区**） |
| **2** | 2 | **4** | 两个并列或递进的核心 |
| **3** | 3 | **5** | 机制 → 方法/对照 → 转折 |
| **≥4** | 合并到 ≤3 | **≤5** | 用多块卡型承载同类，不加卡 |

**配套两条判据**：
- 两个意思**互为因果**、读一张就懂另一张 → **合并**（自问"拆开后某张能独立读懂吗？不能就合并"）；
- 一个意思内部的**多块**（步骤/边界/台词）→ **必须留在同一张**（它们不是独立意思，拆开就是"一屏一句"的空卡）。

**⛔ 三条红线**：
1. **不得为凑到 5 张，把 1 个意思拆成 2 张**——那是空卡。
   **"张数少 ≠ 内容薄"的反面同样成立："张数多 ≠ 内容厚"。**
2. **不得为省事，把 3 个独立意思硬塞进 1 张**——过载。
3. **内容卡 >3 张必须与用户确认**。

**⭐ 新增"可解释"要求（关键）**：张数必须写进 **Gate A 设计文档**——
「**本篇建议 N 张，依据：长文有 X 个独立核心意思 ①…②…③…**」，并说明为何不合并/已合并。
**⛔ 设计文档里只写"5 张"而不给依据，视为不合格**（＝机械执行）。

**另新增**：内容卡少于 3 张时（N=1 或 2）的分工变化说明——
N=1 时这一张要**独自撑起"机制+结论"**（必须做厚）；
N=2 时用 `compare` 让**一张承载对照**，不必为凑数单列一张。
并明确：**同一系列内不必每篇张数相同，张数随内容厚度浮动是正常且被鼓励的**。

## 2026-09-17｜卡片密度：45–65% → **目标带 50–60% / 红线 70%**

### 起因（用户提问）

用户看过第 16–18 篇成品后问：「**正文卡片的文字也比较丰满，是什么考虑**？」

复查后发现问题**不在"丰满"本身，而在"每张都顶到上限"**。

### 实证数据（9 张内容卡）

| 篇 | 卡2 | 卡3 | 卡4 |
|---|---|---|---|
| 16 | 59.6% | 60.6% | **64.0%** |
| 17 | 62.9% | **64.0%** | **64.0%** |
| 18 | 53.9% | 58.9% | 58.9% |

→ **9 张里 4 张正好 64.0%**，全部贴着旧上限（65%）。

**根因**：旧规则只写「45–65% 不超限」——**只有上限意识，没有目标带**。
于是执行时的手感变成"**压到刚好过线就停**"。
**看似合规，实则零余量**：改一处、多一行就破线。

> ⭐ **这与 C11「贴着上限写作＝把风险留给自己」是同一个毛病**——
> C11 说的是描述字数，这里是卡片密度。**同一类错误换了个战场又犯一次。**

### 旧值 → 新值

| 项 | 旧 | 新 |
|---|---|---|
| **目标** | 45–65%（单上限意识） | **目标带 50–60%** |
| **红线** | >65% 即"超标"，但无明确动作 | **> 70% 必须处理**（60–70% 属"可接受但不理想"） |
| **下限** | < 40% 补信息 | **< 45% 补信息** |

### ⭐ 配套：把控制变量从"字数"改为"行数"（本次最重要的可操作化）

**实测发现**：**密度是阶梯式的**——由**排完版后的总行数**决定，**与字数只是间接相关**。
同一段 150 字，**断行差一行，密度差一整档（≈5%）**。

| 卡的结构 | 目标正文行数 | 对应密度 |
|---|---|---|
| 主标题 **1 行** | **7–8 行** | 50–55% |
| 主标题 **2 行** | **6–7 行** | 51–56% |

→ 写作时**边写边数行数**即可自控；**到第 10 行必破 70%**，不必等脚本报错。
（"字数基线"仍可作参考，但**行数更直观、更准**。）

**三条纪律**：
1. **先用"当时的标准"判合规**，再谈"对新标准如何"；
2. **判据要先想清"什么才算真问题"**，再设计匹配方式；
3. **语义类检查必须"真读一遍"**，不能只跑指标。

**⭐ 元规则**：
- **机械匹配只能做"筛子"，不能做"判官"**——命中后必须人工回读确认；
- **黑名单/匹配词越短越误报**（同"亮度找水印必误报"类）；
- **复核报告要先写"我用了什么判据"，再写结论**——判据错了结论全错，**且看起来很像在认真检查**。

**复核内容层最低清单**（此前只核规格，漏了内容）：
① 逐张标注 vs 长文类型声明 ② 卡面动作指令/绝对化 ③ 正文与卡面的**长句级**重复
④ 正文"元叙述"导语 ⑤ 人设连续性 ⑥ 敏感议题边界。

### 为什么值得单立一节

**"复核存量"比"复核新稿"更容易出错**——它套着两套标准（当时的/现在的），
还夹着复核者自己的假设。**而错误的检查比不检查更危险：它会产出"看起来专业的错误结论"。**

**同步**：cache → marketplace（`13-card-article.md` 归一化比对一致）。

## 2026-09-18｜卡片密度目标带 50–60% → **62–68%**，并锁定行距（组合①）

### 用户要求（原话要点）

> 「**最近几篇卡片文章卡片上内容厚度大一些，对于阅读传播是正向的。**」
> 「**选组合1，同步sop**」

**组合①内容**：字号保持 **40px**、行距 **1.78 → 1.66**、上下留白各约 **240px**、
密度目标带 **50–60% → 62–68%**、红线 **70% 不变**。

### 旧值 → 新值

| 项 | 旧 | 新 |
|---|---|---|
| **密度目标带** | 50%–60% | **62%–68%** |
| **密度下限**（补信息） | < 45% | **< 58%** |
| **密度红线** | > 70% | > 70%（**不变**） |
| **正文行距比** | `int(40*1.78)` = 71px | **`int(40*1.66)` = 66px** |
| **正文字号** | 40px | **40px（不变）** |
| **上下留白**（自然结果） | 约 285–350px | **约 225–265px** |
| **单卡正文容量** | ≈ 198 字（9 行） | **≈ 220–240 字（10 行）** |
| **行数判据**（主标题 2 行卡） | 6–7 行 | **9–10 行** |

### ⭐ 决策依据（实测，非体感）

**一、为什么要"更高密度"**

上一轮（09-17）把目标带定在 50–60%，是为防止"贴上限"（C21）。
但用户在「青春期30讲」成品上已确认过 **58–63%** 的观感，并明确：
**"内容厚度大一些，对阅读传播是正向的"** ——
卡片是独立传播单元，读者脱离长文也要读懂，**厚一点利于传播**。

**二、⭐ 关键澄清：留白不是独立参数（本轮最重要的一条）**

```
密度 = 内容块高 ÷ 可用区高
留白 = 可用区高 × (1 − 密度)
```

> **留白是"果"，不是"因"**——由密度与可用区共同决定，**不可独立设定**。
> **压留白不会降密度，反而升密度。**
> → 因此 **SOP 只规定"密度目标带"，不规定"留白数值"**；
> 密度落在 62–68% 时，上下留白**自然**约为 225–265px。

**⚠️ 我在此前的方案里把因果搞反了**：用户说"上下留白太多 → 导致中间密度超标"，
我第一反应是"删文字"。实测后才发现：
- 本系列**不是"留白统一太多"**，而是**留白乱跳（97–364px，跨 267px）**；
- 根因是**同一套版式硬装了 109–233 字（跨 2.1 倍）的内容**；
- **"留白多"与"密度超标"是同一根因的两个表现，不是因果关系。**

**三、为什么用"收紧行距"而不是"缩小字号"来扩容**

| 方案 | 每行字数 | 行距 | 单卡最大正文 | 手机字号 |
|---|---|---|---|---|
| 现状（40px / 1.78） | 24 字 | 71px | 9 行 ≈ 198 字 | 12.6pt ✅ |
| **组合①（本次）** | 24 字 | **66px** | **10 行 ≈ 220 字** | **12.6pt ✅** |
| 字号降 38（38px / 1.68） | 26 字 | 63px | 11 行 ≈ 263 字 | 11.9pt ⚠️ |

**可读性底线实测**（卡片 1242px，手机全屏约 390pt，缩放系数 0.314）：

| 卡片字号 | 手机 pt | 判定 |
|---|---|---|
| 40px | **12.6pt** | ✅ 舒适线 |
| 38px | 11.9pt | ⚠️ 偏小，长内容卡吃力 |
| 36px | 11.3pt | ⚠️ 明显偏小 |

→ **结论：靠"收紧行距 + 提高目标带"扩容，不靠"缩小字号"。40px 是底线。**

**四、留白 ⇄ 密度 对照表**（可用区 1402px）

| 密度 | 内容块高 | 上下各留白 |
|---|---|---|
| 62% | 869px | 266px |
| 66% | 925px | 238px |
| **68%** | **953px** | **224px** |
| 70%（红线） | 981px | 210px |

### ⭐ 本轮新增两个案例

**C22｜复核存量时"核过"≠"核到位"**

## 【2026-09-19】预览默认关闭 · present_files 由"少调用"升格为"默认不调用"

### 起因

用户第三次反馈（截图：界面卡在"生成回复中 present_files"）：
> "你每次到这一步时都非常耗时，查查什么原因，如果是打开预览慢，后面能否不要在自动打开文件预览了，需要查看的我会显示告诉你。"

**关键点：这不是新规则，是 2026-09-10 已写过的规则第三次复发。** 所以本次重点不在"再写一遍"，
而在**查清为什么写了还犯**。

### 测得根因（本次唯一的新信息）

我原以为"文件很小所以不慢"，**实测推翻了这个印象**：

| 对象 | 体积 |
|---|---|
| 单篇发布包正文 `正文_第X篇.html` | **7.5KB**（节点 53、内联 style 50 处、style 占全文 62%） |
| `改善你的亲子关系_全部正文预览_5篇`（本次涉及） | 不大 |
| **`孩子总犯错误怎么办_全部正文预览_6篇.html`** | **1563KB（1.5MB）** |
| `青春期30讲_全部正文预览_18篇.html` | 385KB |

**结论**：慢的不是单篇正文，而是 SOP **强制生成**的「全部正文预览」合并页——
它把 N 篇的内联样式全塞进一页，**体积随篇数线性增长**；
而 `present_files` 打开 `.html` 时**预览面板要完整渲染整页 DOM**。**这才是"每次到这一步都耗时"的直接原因。**

### 为什么规则写了还会犯（三次复发的原因）

**因为"同一约束"被分散在多处，其中一处是"主动指令"，而主约束是"软表述"。**

| 位置 | 原文问题 |
|---|---|
| `04-html.md:55` | **"present_files 时把它排 files 首位"** ← **主动指令，诱导调用** |
| `04-html.md:25` | "每次 present_files 之后也应重跑" ← 默认 present 会发 |
| `08-selfcheck.md:22` | 强制生成合并页 + 详述"一次 present_files 即可完整翻看" ← **把"生成"与"展示"绑在一起** |
| `08-selfcheck.md:23` | "不要每完成一步就自动 present" ← **只禁止"每步"，没禁止"收尾"** |
| `agents/*.md:163` | "**不必每次都调用**……以用户明确指令为准" ← **"不必"太软，且没给默认值** |

**共性错误**：所有版本都在写"**可以少调**"，**没有一处写出默认值**。
Agent 遇到"没说默认值"的软约束时，会按"对用户有帮助"的本能继续调用。
→ **规则只写"上限/许可"、不写"默认值"，等于没写**（与 C21「规则要给目标带，不能只给上限」同源）。

### 本次改法（四处 + 派生版）

把"软表述"全部换成**硬默认值**：**默认不调用；唯一例外＝用户当次明确说"打开/看一下/给我看看"。**

1. `agents/wechat-article-studio.md`（主骨架，每次会话都加载，作用最直接）：
   标题由"`present_files` **不必每次**都调用" → 改为"**默认不调用**"，并写明实测体积数据与用户原话。
2. `references/04-html.md:55`：删掉"**present_files 时把它排 files 首位**"这条主动指令，
   改为"**生成预览文件 ≠ 调用 present_files**"，并新增"预览默认关闭"独立条。
3. `references/08-selfcheck.md`：合并页条目补"生成它绝不含自动打开它"；
   交付条补"**默认动作 = 文字报告路径**"；自检第 11 项补"**不自动 present 就是保持 data-* = 0 的最省事办法**"。
4. 派生版 `_专家/Codex技能/.../SKILL.md`：由"听用户当次指令"补强为"**默认不打开**"（原表述无默认值，同样偏软）。

同步与验证：cache → marketplace 已同步，**MD5 归一化比对 4/4 一致**。

### 与"少确认"的边界（防止再次被误读）

**"默认不交付"只作用于"打开预览/交付文件"这一个维度。**
**Gate 1 / Gate 2 / Gate 3 的确认一次都不能少**——这两件事无关，不得互相推演。
（2026-09-10 已有此教训：曾把"减少 present_files"误推为"可减少确认"，被用户纠正。**本次重申不变。**）
