## 零、本 SOP 的地位与适用范围

### 0.1 它管什么

**每篇公众号长文，额外产出一个「卡片版本」**（微信官方形态名：**贴图**，俗称"小绿书"）。

| 项 | 说明 |
|---|---|
| **适用** | 所有系列、所有长文（存量补做 / 新生成同办） |
| **不适用** | 长文本身的写作与排版（仍走原 SOP 第 0–9 步） |
| **衔接点** | **长文正文完成后**启动；长文是卡片文章的**唯一素材来源** |

### 0.2 与长文 SOP 的关系（一句话）

> **长文是「深度内容」，卡片文章是「轻量分发形态」，两者共享同一份素材、不同的组织方式。**

- 长文：吃**订阅关系**，触达 ≈ 粉丝数 + 社交转发；
- 卡片文章：吃**算法关系**，**不看粉丝数**，优先推给**非粉丝**；
- 卡片文章**底部自动带原文链接** → 陌生人刷到卡片 → 点进长文 → 关注沉淀。

### 0.3 三档优先级如何接入

本 SOP 的规则同样按 `P0 红线 / P1 质量线 / P2 偏好` 三档裁决（与原 SOP 一致）：

| 档 | 卡片文章里包含哪些 |
|---|---|
| **P0 · 红线** | ①平台规格不违背 ②**每张卡印改编标注** ③不杜撰（回溯长文）④不加动作指令/不绝对化 ⑤不标原创/不填作者 ⑥Gate 关卡 |
| **P1 · 质量线** | 张数控制、封面卡抓眼球、内容卡信息完整、三件交付物齐备、体积/比例合规、自检通过 |
| **P2 · 偏好** | 配色、底图意象、话题标签数量 |

**已知冲突的既定裁决**：
- **内容完整 vs 张数少** → **两者都要**：张数收敛到 5 张，靠**每张内容做厚**解决（不是靠加卡）。
- **体积极小 vs 画质** → **柔化底图**解决（文字是后画的，不受影响）。
- **封面卡抓眼球 vs 改编标注可见** → **标注进 16:9 安全区**，两者不冲突。

## 一、形态定义

```
卡片文章 = 封面卡 × 1 + 内容卡 × N + 收尾卡 × 1（N ≤ 3）
         + 卡片正文（纯文本，含话题标签）
         + 字段表（标题 / 无作者 / 描述指引 / 标签）
```

### 1.1 它不是什么（三条禁令）

| ⛔ | 说明 |
|---|---|
| **不是**"把长文拆成几张图" | 要**重新组织叙事节奏**，按"一屏一段"重新分屏 |
| **不是**"长文摘要截屏" | 卡片图是**重新排版的文字卡**，不是正文截图 |
| **不是**"长文的缩略版" | 它是一份**独立成型**的内容，单看卡片也能读懂 |

### 1.2 平台机制（为什么要做）

| 机制 | 依据 |
|---|---|
| 贴图走**算法推荐**，**优先推给非粉丝** | 后台提示语原文："发布后优先推荐给非粉丝用户，触达更多新读者" |
| 官方力推：过去一年 **1.16 亿篇**贴图、同比涨 **377%**；近一月活跃号 **52% 用过** | 微信《公众号14周年创作者报告》2026-08-17 |
| **粉丝少 + 内容大众向的号最受益** | 行业双号实测：专业深度内容/大粉丝号效果不明显 |
| 本账号契合度：**粉丝极少（送达 32–85）+ 家庭教育天然大众向** | 项目数据 |

> **结论：本账号是贴图红利最精准的受益人群**，而系统的自动生成版**封面难看、描述被截、无标签**，**必须自做才能拿到流量**。

## 二、⭐ 平台规格（**官方口径 · 不可违背**）

> **纪律**：本节凡标 ✅**官方** 的，一律**不得凭印象改写**；标 ⚠️**实测** 的可作依据但不得当平台承诺。

| 项 | 规格 | 强度 | 出处 |
|---|---|---|---|
| **正文格式** | **仅纯文本** + 部分特殊功能标签（如商品） | ✅ **官方** | 开发者文档 `draft_add/update` |
| **标题上限** | **32 字** | ✅ **官方** | 同上（"总长度不超过32个字"） |
| **图片张数** | 最多 **20 张**（首张即封面图） | ✅ **官方** | `image_info` 字段说明 |
| **展示比例** | **3:4**（最佳展示尺寸） | ✅ **官方** | 微信派 / 开发者文档 |
| **封面展示比例** | **16:9**（可选 1:1 / 2.35:1） | ✅ **官方** | `cover_info.ratio` |
| **作者字段** | **无**（newspic 结构无 author） | ✅ **官方** | 官方示例结构 |
| **能否标原创** | **不能** | ✅ 多源一致 | — |
| **标题+正文总字数** | **≤ 1064 字** | ⚠️ 实测一致 | 多源实测 |
| **占用群发通知额度** | **占用**（一天仅一次） | ✅ 本项目数据印证 | 见 `发布数据复盘.md` |
| **必须勾选"允许被推荐"** | 否则**公域入口锁死** | ✅ 多源一致 | — |
| **编辑器富文本** | **不支持** | ✅ **官方** | 同"正文格式" |

### 2.1 ⛔ 最重要的一条（官方原文）

> **「图片消息则仅支持纯文本和部分特殊功能标签如商品」**
> —— 对照图文消息：「**支持HTML标签**」

**逐项含义**：

| 能力 | 长文（news） | **贴图（newspic）** |
|---|---|---|
| 加粗 / 斜体 / 下划线 | ✅ | ❌ |
| 字号 / 颜色 / 背景色 | ✅ | ❌ |
| `<section>` / `<p>` 等标签 | ✅ | ❌ 会当纯文本或过滤 |
| `<img>` 插图 | ✅ | ❌（图只能走卡片图列表） |
| **分段** | HTML 控制 | **靠空行** |
| emoji / 符号 | ✅ | ✅ |
| 超链接（小程序 / 网站） | ✅ | ✅ |

> **⛔ 由此产生一条纪律**：项目的《微信公众号排版HTML规范》（section 流式、零 `data-*`、标签白名单）
> **只适用于长文正文**，**对卡片正文完全不适用**——卡片正文是**纯文本**，不要塞任何标签。

### 2.2 ⚠️ 封面按 16:9 展示 → 必须设安全区

**这是本次踩到的最隐蔽的坑**：首图作封面时按 **16:9 中心裁切**展示，
而卡片本身是 3:4 → **裁切带只占卡片中间约 42%**。

```
1242×1656 卡片 → 16:9 裁切带 = y 478 ~ 1177（高 698px）
```

**→ 封面卡的所有关键内容（改编标注、主文案、署名）必须落在该带内**，否则对外展示时消失。

**自检断言（必须写进脚本）**：
```python
y0, y1 = int((H - W*9/16)/2), int((H + W*9/16)/2)   # 478, 1177
assert 所有文字块 b[1] >= y0 and b[3] <= y1          # 仅封面卡强制
```

### 2.3 两套规格别混（长文封面 vs 卡片）

| 用途 | 比例 | 体积 | 说明 |
|---|---|---|---|
| **长文封面**（原有） | **2.35:1**（1200×511） | ≤200KB | **规则不变** |
| **卡片图**（新增） | **3:4**（1242×1656） | **<100KB** | 竖屏滑动卡片 |
| 卡片图**作贴图封面时** | 系统按 **16:9** 裁切展示 | 同上 | **需设 16:9 安全区** |

## 三、⭐ 张数规则

| 项 | 值 | 依据 |
|---|---|---|
| **平台上限** | **20 张** | 官方 |
| **实测最优** | **2–3 张** | 多源实测同向 |
| **掉量拐点** | 5 张以上开始掉、8 张以上断崖 | 同上 |
| **本 SOP 默认** | **封面 1 + 内容 ≤3 + 收尾 1 = 共 5 张** | 用户要求 + 实测吻合 |
| **内容卡上限** | **3 张** | 用户明确 |
| **超出怎么办** | **必须与用户确认**（不得自行增加） | 同上 |

### 3.1 机制：为什么"张数越多越掉"

**2026-03 改版后**：用户**不必横滑看完所有图**，**直接往下滑就能看到下方正文、广告、留言区**。

> 实测资料原话：**"翻图不赚钱，往下滑才赚钱。"**
> 贴图的阅读数据与广告收益**全靠竖向滑动触发**。

所以：**张数一多 → 用户翻几张就累了 → 直接退出 → 根本不会往下滑 → 有阅读、无收益、无推荐。**

> **⚠️ 反直觉但重要**：**翻图多 ≠ 好，反而是负资产。**
> 官方上限 20 张 ≠ 该用 20 张。**"上限是多少"与"该用多少"是两件事。**

### 3.2 5 张的叙事分工（默认骨架）

| 卡 | 角色 | 承载 |
|---|---|---|
| 1 | **封面卡** | 抓眼球的总钩子（≤20 字，只负责让人停下） |
| 2 | **内容卡①** | **核心机制**（为什么会这样） |
| 3 | **内容卡②** | **对照 / 方法**（该怎么看） |
| 4 | **内容卡③** | **转折 / 时间线**（那我该等多久 / 我做了什么） |
| 5 | **收尾卡** | 情绪落点 + 承接原文 |

**为什么内容卡只要 3 张**：滑动越长、单卡信息越碎。**3 张足够承载一条完整叙事线**（机制 → 方法 → 转折）。
宁可在卡片里**更狠地取舍**，也不把长文切片搬过来。

### 3.3 ⛔ 本次的教训

**v1 曾设计 8 张**，与"张数越多越掉量"的实测结论**直接冲突**，后收敛为 5 张。
**→ 定张数前必须先查平台实测，不能凭"内容多放几张更充实"的直觉。**

| 文件 | 放什么 | **⛔ 不放什么** |
|---|---|---|

### 4.1 ⛔ 本次的教训（两条）

1. **字段表里存了两处正文**（完整全文 + 一整节"描述/正文"介绍）→ 违反"单一真相源"。
   **已改为：字段表只放后台要填的字段。**
2. **正文文件缺话题标签** → 已改为**标签写在正文末行**，粘贴时一并带入，

### 4.2 命名规范

```
卡片_NN_短标签.jpg        两位序号保证排序；短标签取该卡核心意象（"封面""腌萝卜""时间线"）

```

### 4.3 目录落位（**目标结构，后续标准动作**）

```
<系列>/公众号文章/发布包_第X篇_xxx/
├── 长图文发布包/           ← 长文三件套（正文.html / 01字段 / 封面.jpg）
└── 卡片发布包/             ← 卡片交付物（01字段 / 02正文 / 卡片_NN.jpg）
```

**⚠️ 迁移前必做**：改造 3 个工具脚本，否则自检链路全断。

| 脚本 | 现状假设 | 需改造为 |
|---|---|---|
| `系列发布全套自检_selfcheck.py` | `发布包_*` 下**直接**找文件 | 优先查 `长图文发布包/`，**回退**包根 |
| `重建全部正文预览.py` | 同上 | 同上 |
| `模板感诊断_template_scan.py` | 同上 | 同上 |

## 五、⭐ 内容撰写规则

### 5.1 标题（上限 32 字）

| 规则 | 说明 |
|---|---|
| **钩子在前 10 字内** | 系统按**前 20 字**截断展示 |
| **≤20 字优先** | 留出余量，避免被截 |
| **可≠长文标题** | 卡片版应重新起，更适合信息流 |
| **优先"冲突/反差"句式** | 如"我忍了20天没吼他，他一点没变"——有具体数字 + 有反差 |

### 5.2 摘要 / 描述 = **正文**（不是长文的摘要）

> ⭐ **关键认知**：卡片文章的"描述"**不是长文摘要**，而是**卡片文章的正文**。
> 实测机制：新版贴图里用户**直接往下滑就能读到它**，广告收益也靠"往下滑"触发。

| 规则 | 说明 |
|---|---|
| **字数** | 标题+正文 **合计 ≤1064 字**；建议正文 **900–1000 字**，留 50+ 字余量 |
| **开头 3 行内进场景** | 系统从**开头约 200–260 字**截取做预览，**开头写好=贴图效果好** |
| **第一句直接给处境** | 不写"本文讲述……"这类导语；读者大概率**不认识这个号**，不依赖既有信任 |
| **结尾给情绪落点** | 不写"点赞/转发/关注"等**动作指令** |
| **回复长文主干** | 承载长文主线，让卡片文章**单篇可独立成文** |

### 5.3 卡片文案

| 卡 | 规则 |
|---|---|
| **封面卡** | **全卡 ≤20 字**；分 2–4 行；**不塞正文、不塞观点** |
| **内容卡** | **一张一个完整意思**；**每张信息自足**（单独看也能读懂）；建议 60–150 字 |
| **收尾卡** | 用长文最有力的一句收；可含一小段场景承接 |

**⭐ 内容卡必须做"厚"**（本次用户明确纠正）：

| ⛔ 错误做法 | ✅ 正确做法 |
|---|---|
| 只放一句金句 | **主题标签行 + 主标题 + 足够读懂的正文段** |
| 读者"没头没脑" | **每张卡顶部标出"这张讲什么、讲到第几步"**（如 `② 先弄明白：改变到底是怎么发生的`） |

> **纪律：张数少 ≠ 内容薄。** 张数收敛到 5 张，**代价要用"每张做厚"来还，不是用"多加几张"来还**。

### 5.4 话题标签

| 规则 | 说明 |
|---|---|
| **数量** | 建议 **6–10 个**；样本实测可带 19 个 → **不是硬上限** |
| **位置** | **写在正文末行**（粘贴时一并带入） |
| **待实测** | 后台是否有独立标签入口 → 有则再填一次，无则依赖行内 |

### 5.5 ⛔ 红线（沿用长文纪律 + 卡片特有）

| # | 红线 | 说明 |
|---|---|---|
| 1 | **不杜撰** | 所有观点/比喻/金句**必须能回溯到长文**；长文又能回溯到原材料 |
| 2 | **不加动作指令** | 不写"点赞/转发/关注"（外部资料大量建议引导互动，**与本号纪律冲突，一律不采纳**） |
| 3 | **不用绝对化** | 不写"一定/必然/彻底治好" |
| 4 | **人设一致** | 孩子 **15 岁·高一·儿子**；叙事者"一个也在重启的爸爸" |
| 5 | **敏感议题带边界** | 涉及厌学/自伤等须给专业求助提示 |
| 6 | **不填作者、不标原创** | 平台无该字段 |
| 7 | **⭐ 每张卡印「课程学习心得 · 家庭场景改编」** | **卡片特有 P0**，见 5.6 |

### 5.6 ⭐⭐ 卡片特有的 P0 红线：**逐张标注**

> **卡片是独立传播单元**——一张卡可能被**单独看到、单独转发**，
> 而长文的"第一屏标注一次"策略**在卡片形态下失效**。

| 形态 | 改编标注策略 |
|---|---|
| 长文 | **第一屏标注一次**即可 |
| **卡片文章** | **每一张卡都必须印**（顶部第二行） |

**判定**：只要卡内出现**第一人称叙述**（"我忍了20天""我是汤刚调好"），该卡就**必须**带标注。

**⚠️ 且标注必须落在 16:9 安全区内**（封面卡），否则对外展示时会消失——本次踩过此坑。

## 六、⭐ 技术实现（生成路线）

### 6.1 ⛔ 绝对路线：AI 出**无字底图** → 脚本叠中文

| 步骤 | 做法 |
|---|---|
| ① 底 | AI 生成**不含任何文字**的底图；或用 Pillow 画纯色/渐变底 |
| ② 字 | **Pillow + 微软雅黑**（`msyh.ttc` / `msyhbd.ttc`，本机已确认可用）精确叠加 |

**⛔ 为什么必须这样**：**AI 写中文极易出错字、乱码、糊字**（项目既有铁律）。
卡片**靠文字传递信息，一个字错就全废**。

**⛔ 用户明确的禁令**：**不用 HTML 转图片**。卡片图由脚本直接生成。

### 6.2 底图配比（省积分）

| 卡 | 底图 | 成本 |
|---|---|---|
| **封面卡** | AI 底图 | 消耗积分（约 5–10 分/张） |
| **收尾卡** | AI 底图 | 消耗积分 |
| **内容卡** | **纯色底**（Pillow 画） | **零成本**，且更适合承载密集文字 |

> **每篇只需 2 张 AI 底图**。**生成前必须告知用户消耗积分。**

### 6.3 底图后处理流水线（脚本化，参数固定）

| 步骤 | 参数 | 目的 |
|---|---|---|
| ① 去水印 | 顶锚裁到 3:4 高度 | 平台水印固定在最底部，裁切线之下自然出框 |
| ② 统一 3:4 | 横向居中裁 | **只裁不放** |
| ③ 缩放 | → 1242×1656；**放大倍数上限 1.30** | 超限即重生，防糊 |
| ④ 保护性暗化 | veil 0.14–0.26，色 `#241c14` | 保证浅色字可读 |
| ⑤ **轻微柔化** | `GaussianBlur(1.0–4.2)` | **减高频噪点 → JPEG 压缩率大幅提升** |
| ⑥ 顶部压字区 | 渐变暗化，strength 0.30–0.52 | 大字专用 |

### 6.4 ⭐⭐ 本次最大的技术坑：**底图不柔化就压不进 100KB**

| 场景 | 结果 |
|---|---|
| AI 底图**不柔化** | 封面卡压到 **q=40 仍 102.7KB** ❌ 超限 |
| AI 底图**柔化后** | **q=50 即 98.9KB** ✅ 通过 |
| 收尾卡（文字最密） | 需 **blur=4.2 / veil=0.44**，q=33 → 96.0KB |

> **原理**：**柔化只作用于底图**；**文字是后画的，清晰度完全不受影响**。
> 底图仅作氛围，柔化后反而更像景深虚化——**视觉更好，压缩更容易，双赢**。
>
> **→ 纪律：底图一律柔化，不要试图用"降 q"硬压。**

### 6.5 文字排版引擎（**必须写扎实**）

> ⛔ **背景**：首次技术验证时，"逐字绘制"与"整行绘制"混用，**导致两行文字重叠**。
> 这不是"能不能做"的问题，是"排版引擎要写扎实"的问题。

**五条纪律（缺一不可）**：

| # | 纪律 | 目的 |
|---|---|---|
| 1 | **只用一种绘制方式** | 所有文字经统一出口，不混用逐字/整行绘制 |
| 2 | **先算后画** | 先算元素总高 → 定位 → 再逐块绘制；**绝不用绝对 y 硬写** |
| 3 | **行首禁则** | `。，、；：！？）》”’%…·` 不出现在行首 |
| 4 | **块内垂直居中** | 内容块在可用区内居中（防"重心偏上、下方大留白"） |
| 5 | **渲染后自检** | 断言**越界 + 重叠 + 体积 + 16:9 安全区** |

### 6.6 ⭐ 自检断言清单（脚本必须写死）

```python
# 1. 尺寸与比例
assert (w, h) == (1242, 1656) and abs(w/h - 0.75) < 0.001

# 2. 体积（用户硬要求）
assert kb <= 100

# 3. 越界（含容器框）
for b in BOXES + CONTAINERS:
    assert b[0] >= 14 and b[1] >= 14 and b[2] <= W-14 and b[3] <= H-14

# 4. 重叠（⚠️ 容器框不参与重叠比较，否则误报）
for i, j in combinations(BOXES, 2):
    assert not (overlap_x > 6 and overlap_y > 6)

# 5. ⭐ 封面卡 16:9 安全区（本次新增，最关键）
if is_cover:
    y0, y1 = int((H - W*9/16)/2), int((H + W*9/16)/2)
    for b in BOXES:
        assert b[1] >= y0 and b[3] <= y1

# 6. 正文字数
assert len(正文) + len(标题) <= 1064
```

### 6.7 ⚠️ 两个 Windows 环境坑（已踩过）

| 坑 | 现象 | 修法 |
|---|---|---|
| **文件被占用** | 保存时报 `PermissionError` / `OSError: [Errno 22]` | **保存加重试**（6 次，间隔 0.4s） |
| **体积超限未计入失败** | 出现 195KB 却报 ✅ | **超 100KB 必须记失败**，不能只看"保存成功" |

### 6.8 ⚠️ 水印检测的教训

**用"亮度阈值"找水印在自然图像上必然误报**——木台面高光、瓷碟边缘都会被判成水印。

**✅ 正确做法**：
1. 脚本只做**裁切**（按 3:4 顶锚裁，让水印自然出框）；
2. 脚本**输出底部条带图**；
3. **人工目检是最终判据**（不看算法结论）。

## 九、⭐⭐ 错误案例库（**本项目真实犯过的 15 处错**）

> **用法**：每一步动手前，扫一眼本节对应条目。**这些不是假设，是真实踩过的坑。**
> 分类：**A 平台规则错 / B 交付物错 / C 技术错 / D 数据与认知错**

### A · 平台规则类（来源：未先查官方文档就动手）

| # | 错误 | 正确做法 | 教训 |
|---|---|---|---|
| **A1** | 以为贴图正文**支持富文本**，按长文 HTML 规范设计 | **官方：仅纯文本** | **先查官方文档，再设计** |
| **A2** | 标题上限写 **64 字** | **32 字**（64 是图文消息的） | 长文/贴图的规格**别互相套用** |
| **A3** | 卡片张数上限写 **9 张** | 官方 **20 张** | 别拿早期资料当现行口径 |
| **A4** | 描述上限写 **100 字** | 标题+正文 **≤1064 字** | 规格要查三处：官方文档 / 实测 / 后台 |
| **A5** | 字段表里填了**作者** | 贴图**无 author 字段** | 长文的字段不能照搬到卡片 |
| **A6** | 不知封面按 **16:9** 展示 → 封面卡文字被裁 | **设 16:9 安全区**（y 478–1177） | 官方 `cover_info.ratio` 有明确说明 |

> **⛔ 动手设计前，先查官方文档（developers.weixin.qq.com）+ 平台实测。**

### B · 交付物类

| # | 错误 | 正确做法 | 教训 |
|---|---|---|---|
| **B1** | 字段表里**存了两处正文**（全文 + 一节介绍） | 字段表**只放后台要填的字段** | **单一真相源** |

| **B3** | 内容卡**文字太少**（只一句金句）→ 读者"没头没脑" | **每张做厚**：主题标签 + 主标题 + 完整正文段 | **张数少 ≠ 内容薄** |

### C · 技术类

| # | 错误 | 正确做法 | 教训 |
|---|---|---|---|
| **C1** | 排版引擎**逐字/整行绘制混用** → **两行文字重叠** | **只用一种绘制方式** | 排版引擎要写扎实 |

### D · 数据与认知类（**最危险，会污染所有后续判断**）
