# 维护·素材池·数据复盘（第 10–12 步）

**第 10 步 · 维护、巡检与清理（用户说"清理一下/整理一下目录"时走这里）**

> 背景：内容生产会不断沉积过程文件——备份快照、派生预览页、带水印原图、未采用候选图、一次性调试脚本。工作空间会越来越臃肿，且**过程文件混进发布包会破坏"打开即用"**。本步是维护流程，与内容生产解耦。

- **【⭐ 三层防线：文案规范类问题的防治体系（2026-09-21 建立）】** 微信排版问题分三层拦，**前两层不可省**：
  1. **生成阶段（前置，最省事）**：`04-html.md` 的 **R1–R5 生成硬性规则**——写正文时就按官方规范写（块内不混排、控嵌套、不写 `font-family`、背景写公共容器…）。**绝大多数问题在这一层就消失。**
  2. **交付前自检（项目工具，快）**：`系列发布全套自检_selfcheck.py` + `wx_html_fix.py --check`。
     ⚠️ 这两个是**启发式筛查**，**不是官方判定的复现**（Python 无法跑真实布局）。
  3. **官方结构检测（后置兜底，权威）**：`工具脚本/wechat_official_verify.py`（真机 puppeteer，全 17 条规则）。
  - **⛔ 关键认知（实操教训）**：**不能只依赖第 3 层**。官方规范共 22 个章节，检测器只覆盖 15 个；**7 个章节完全不查**（见下）。所以「官方检测通过」**≠**「符合文档」，**第 1 层永远不可省**。
    - **唯一「函数已实现但未接入」的**：`font-family`（`engine/rules/font-family.ts` 有 `checkFontFamilyViolation()`，但 `collect.ts` **调用 0 次**）→ 本项目 **91 篇**写了自定义字体仍判"通过"。
    - **其余 6 个章节连实现都没有**：`4.2.1 背景容器`、`4.2.2 嵌套关系`（部分并入 `nestNodes`）、`4.3.1/4.4.1 图片承载纯文本`、`4.3.2 透明底图`、`4.3.3 补色机制`、`4.5.2 !important`。
    - 随时可查：`python 工具脚本/wechat_official_verify.py --list-rules`（会一并打印这 7 条）。
  - **⛔ 另一条**：官方检测结果**按规则名分组**（`line-height` / `nestNodes` / `width`…），**不同规则互不相干、必须分别处置**。曾把 `nestNodes`（嵌套层级）误当成「行高没修净」而白追一轮。
  - **官方三条命令**（工具已全部封装；URL 抓取是官方 README 的规划项，**未实现**）：
    | 命令 | 用途 | 工具入口 |
    |---|---|---|
    | `check` | 全规则检测（puppeteer 真机） | `wechat_official_verify.py <file>` / `--dir` / `--all` |
    | `dedupe` | **清理冗余嵌套**（jsdom 真删）→ 治 `nestNodes` | `wechat_official_verify.py --dedupe <file>`（`--dry-run` 预览） |
    | `probe` | 环境探针（验证 puppeteer + 全规则跑通） | `wechat_official_verify.py --setup` |
  - **dedupe 使用纪律（2026-09-22 实测）**：它输出的是**正文片段**，会丢 `<html>/<head>/<title>/<body>` → 工具已**自动回填外壳并保留 title**，可直接粘贴。已知格式归一（HTML 等价、不影响显示）：`<br>`→`<br/>`、属性引号统一双引号、缩进重排。**安全判据 = 剔除标签后的可见文本逐字一致**（工具会逐篇显示 ✅/❌）。实测《你是孩子最好的玩具·第1篇》：`nestNodes 4 → 0`，文本逐字未变。
- **【⭐ 批量修复纪律（2026-09-21 实证，51 篇修复提炼）】** 凡对多篇正式成果做结构性批量修改（如包 span、改标签）时：
  1. **先提交回滚点**（`git_sync.py`），再动手。
  2. **整批备份**到 `_备份/<对象>修复前_<时间戳>/`，**保留原目录结构**。
  3. **分批写入**（每批 ≤10 篇），**逐批核对**后才继续。
  4. **纯度断言（最关键）**——证明「只做了该做的改动」：
     - 纯文本（剔标签后）**逐字一致**；
     - 标签配平（section/p/span/b/strong）；
     - **剔除全部新增标签后与原文逐字一致**（如"剔除全部 `<span>` 后与原文完全一致"→ 证明只加了 span）。
     ⚠️ 剔除时**必须用 `re.sub(r"</?span[^>]*>", "", s)` 这类"删标签"方式**，**不要用"匹配 `<span>` 内容"的方式**——原文已有 span 时会错乱，会误报"14 篇不一致"（实测踩过）。
  5. **修完必须重建预览 + 跑全套自检**（`--legacy` 应全通过）。
  6. **幂等**：修复函数应可反复运行（已修的块自动跳过）。
- **【⛔ 改完 `工具脚本/*.py` 的验收纪律（2026-09-22 事故后确立）】** 大段替换代码（尤其**用注释行当替换边界**）后：
  1. **必跑静态体检**：`python 工具脚本/py_ast_health.py`，**退出码必须为 0**。
     它用 AST 找出「被调用但未定义」的名字——正是"边界吞掉一个函数"会产生的隐患。
  2. **测试必须覆盖每条分支**，不能只跑最短路径。
     ⚠️ 实证：某次替换把 `report()` 整段删掉，而 `--setup`/`--dry-run`/`--list-rules`
     **三条路径都在到达它之前就 return 了** → 三次手工测试全部"通过"，
     真正的 `NameError` 只出现在**默认检测路径**上。
  3. **用注释当替换边界时，边界内的内容必须先打印并逐项确认**（打印了却没比对 = 没看）。
  4. **改动写入后，至少真跑一次"最长路径"**（如实际的 `--dedupe` 写回 / 默认检测），再看退出码。
- **【⛔ P0 · 三步安全清理法】** 用户说"扫描清理一下"时，**第一轮只读扫描、绝不删任何文件**：
  1. **只读扫描 + 出报告**：列出所有候选（备份目录 / 过程脚本 / 临时文件 / 原始图 / 候选图 / 派生预览页），统计体积与文件数，**按三类归档**——
     - **A 类 · 建议删除**：可重建或已过期（派生预览页、旧版备份、被取代的旧脚本、历史快照）
     - **B 类 · 建议保留**：有回归价值（**本轮修复前的快照**——留到发布验证通过后再清；体积极小的备份）
     - **C 类 · 需用户确认**：原始素材类（带水印原图、未采用候选图）——**涉及素材，绝不擅自处置**
     - 同时给出 D 类"顺手可整理"（不删只挪位，如发布包内混入的过程文件）
  2. **等用户圈选**：报告里给出 2–3 个方案（稳妥 / 稳妥+归档 / 深度清理），请用户圈定范围。**未收到明确删除指令前，禁止执行任何删除或移动。**
  3. **分批执行 + 逐批核对**：每批 ≤10 项，每批后核对工作区真实状态、异常立即停。
- **【⛔ P0 · 只走回收站】** 统一用系统回收站（`send2trash`），**禁用 `rm -rf` / 不可逆删除**；执行前把完整清单（原路径+体积）写入 `.workbuddy/_清理清单_<日期>.md`，便于按原路径找回。清理前建议**先 git 提交一次**，把当天工作固化进历史，让后续删除都可回滚。
  - **⚠️ 但 git 只在"目录被跟踪"时才兜底**：过程目录通常**已被 `.gitignore` 排除 → 全部未跟踪 → `git commit` 对它们毫无作用**（2026-09-21 实测：29 个待清项**无一个**被 git 跟踪）。
    → **清理前必须先 `git ls-files --error-unmatch <路径>` 实探**；未跟踪时，**回收站就是唯一退路**，清单留档不是可选项而是必需项。
- **⚠️ 关键坑：`send2trash` 在中文路径下会误报失败（实证）**：明明**已成功移入回收站**，却抛 `FileNotFoundError [WinError 2]` 或 `PermissionError [WinError 5]`。
  - **绝不能用它的返回值/异常判断成败**——必须以 `os.path.exists()` **复核工作区真实状态**为准；路径**必须用绝对路径**（相对路径更易触发误报）；并对路径做**工作空间前缀校验**，防止越界误删。
  - 验证"是否真的进了回收站"：解析 `D:\$Recycle.Bin\<SID>\$I*` 元数据（结构：8字节版本 + 8字节文件大小 + 8字节删除时间 + 4字节名字长度 + UTF-16 原名）。**`PowerShell` 的 `New-Object -ComObject Shell.Application` 在受限环境会被安全策略拦截，不能用来读回收站。**
  - ⭐ **"抛异常"与"真失败"要分开处理**：目录级调用**真的失败**时（复核后目录与文件仍在），**降级为「逐文件入回收站 + 最后单独清空目录」**——2026-09-21 实例：某 `_预览` 目录级连试 2 次均真失败（6 文件仍在），**改为逐文件后 6/6 全部成功**。
    → 另有一种"**部分删除**"：内容已进回收站、却留下空目录骨架 + 个别残留文件（实测留 2 个 jpg）→ **重试一次即可收口**。
  - ⚠️ **运行环境**：系统 python 常缺 `send2trash`/`pywin32` → 用隔离 venv（本项目为 `binaries/python/envs/default`，两者齐备）。
- **【清后复检必做·预期副作用】** 清理 A 类 `_预览/` 后，`系列发布全套自检_selfcheck.py` 的**【8】合并预览页必然报 ❌**（该项正是检测预览页存在性）。**这是预期副作用，不是成果损坏**——其余各项（发布包三件套/标题一致/来源声明/结构规范/`wx_html_fix`/data- 零残留）应仍全 ✅。
  → **正确顺序：先重建预览 → 再跑自检**，此时应回到全系列通过。**否则会把预期副作用误判为"清理弄坏了正式成果"而走错排查方向。**
  - **重建预览优先用「各系列自带的 `_build_preview.py`」**：它们统一输出到本系列 `_预览/`，符合保留期与 `.gitignore` 约定。
  - ⚠️ **`工具脚本/重建全部正文预览.py` 曾把预览页写到系列根目录**（2026-09-21 修）：后果是**逃出 `_预览/` 约定 → 逃出 `.gitignore` 与保留期管理，并被误当正式产物**。已改为输出 `_预览/`。
  - ⚠️ **结构迁移必须连脚本一起扫**：SOP 改结构后，散落在各系列的旧 `_build_preview.py` **不会自动跟进**。
    实测某系列仍用旧的 `发布包_第*篇_*/正文_*.html` 模式 → **不认新结构 `长图文发布包/` → 生成 `_预览_0篇.html`**（静默产出空预览）。
    → 重建后**必须核对预览页篇数**（`含 N 篇正文`），别只看"文件生成了"。
- **【清后复检的额外价值】** 复检不只是"确认没弄坏东西"，它常能**翻出一直潜伏的存量 bug**（2026-09-21 一次复检揪出 3 个：通用脚本输出错位、系列脚本不认新结构、自检判据漏配导致误报）。
  → **复检报错先分"预期副作用 / 清理致损 / 存量 bug"三类**，逐类定性再动手；**归属未查明前不要改任何成品**。
- **【区分"历史约定"与"过程文件"】** 清理时最容易误伤的是**旧系列的历史约定**：
  - `02_发布操作指南.*`（**不再生成新篇**）——**凡已存在的一律保留、不删**（含新系列已产出的那批）；新篇不再生成，也不要反向"补齐"。
  - 早期发布包缺 `01_字段表`（解码青春期等）——历史差异，不是缺陷；
  - 各系列来源声明口径不同（课程类 / 读书笔记类 / 原创真实经历类）——均合规，不得统一"修正"。
  - **新结构发布包的两个子目录**（`长图文发布包/`、`卡片发布包/`）——**正式交付物，不是过程文件**，
    不在白名单外的清理范围；**旧结构包根的三件套同理**。清理时两者都**不得列为多余项**。
  - **原则：清理只针对"过程产物"，绝不动任何正式成果与历史约定。**
- **【过程文件"挪"不"删"】** 未采用的封面候选图、生图与后处理脚本（`_cover_proc.py` 等）**移到该系列 `公众号文章/_过程文件/`**保留（候选图留有可复用的提示词与参数）；带水印原图移到 `_原始图归档_日期/`。**直接删除会丢失可复用资产。**
- **【跨系列巡检】** 用户要求"检查一下各系列"时，用通用脚本逐系列跑（新系列严格模式、既有系列 `--legacy`）：
  ```bash
  python 工具脚本/系列发布全套自检_selfcheck.py --dir "公众号/<系列>/公众号文章" --legacy --source "扶鹰教育-王金海"
  ```
  发现的问题**分四类报告（技术+内容双维）**：
  - **① 明确缺陷**：真实性冲突（虚构冒充实录）、人设或年级冲突、无据数字、来源错配、高风险误导、`data-*` 污染、标题三处不一致 → **备份后修复**。
  - **② 历史写法差异**：02 指南是 .md、来源口径不同、早期包无 01 字段表 → **不是缺陷，不动**（见上条"区分历史约定与过程文件"）。
  - **③ 质量优化**（新增维度，**技术合格 ≠ 内容合格**）：标题同质、语言指纹重复、系列过长（超 5 篇且非材料厚实）、方法空泛、视觉识别分散、篇幅明显偏离区间、五层完整性缺项 → **列出建议但不擅自批量改**。
  - **④ 需要用户判断**：真实经历确认、叙事边界、标题风格偏好、发布数据解读、标题版本冲突（无可靠依据时展示两版再确认）→ **问用户**。
  - **⚠️ 只读巡检只给建议，不自动修改存量正文**；用户要求修复时，在已授权范围内处理"明确缺陷"并复检，无须重复请示。**技术自检全部通过 ≠ 内容质量已经通过**——两类都要报。
  - **红线：不擅自批量改动历史已发布成品**——整体重制的风险高于收益。发现存量问题时**先报告，由用户决定是否修**。
- **【清理后必做复检】** 清理/移动完成后，重跑全套自检确认正式成果零影响（如"15/15 系列通过"），并核对：发布包内非标准文件残留 = 0、git 索引中过程文件 = 0、`.gitignore` 规则生效。
- **【合并系列与阶段目录收口】** 合并旧系列时，先把课程原件、逐字稿、原图等原始资料复制进新系列 `原始材料/`，生成文件清单与 SHA256 并逐一核对；旧正文、旧封面等生成成果不得冒充原始资料。只有新系列长文、封面、卡片、手册、预览、上传清单和自检全部完成，且用户明确授权后，旧系列才退出。记录旧目录文件数、总大小、迁移位置与绝对移除路径；若只能确认源目录消失而不能枚举回收站恢复项，必须明确写“恢复位置未能独立验证”。清理 `样板_*` 等阶段目录前还要搜索脚本与预览调用方，切换到正式包并重建预览；清后再次搜索残留引用并跑全系列自检。
- **⭐【2026-09-11 新增·过程文件"定时过期"机制（治本，取代"想起来才清"）】** 过程文件天然随时间累积，靠人工记着清不现实。因此按**"可重建性"分级设定保留期**，由脚本定期扫描提示：
  - **四类与默认保留期**（越"可重建"留得越短）：
    | 类 | 内容 | 默认保留 |
    |---|---|---|
    | **A** | 完全可重建（`_预览/` 合并预览页等，脚本随时重建） | **7 天** |
    | **B** | 一次性快照（`_backup*` / `_备份/`，修复前备份，验证通过后即失效） | **7 天** |
    | **C** | 素材类（`_封面候选/` `_过程文件/` `_未采用*/` `_原始*/` `_归档*/`，含可复用提示词与参数） | **14 天** |
    | **D** | 长期归档（`_档案/` `_资产/`，报告与长期资产） | **不过期** |
  - **⚠️ C 类删除前必须"先摘提示词"（14 天较短，易丢资产）**：C 类里最值钱的是**封面候选图的生成提示词**（含意象、光线、镜头、约束词），删图不心疼、**丢提示词要重写**。因此清理 C 类前逐条检查：
    - 候选图 / 过程文件 → 把该篇的**最终采用提示词**（或"意象 + 关键约束"）**摘录进该系列发布手册**（新系列 `03_发布手册.md`；存量系列沿用其现有手册名）的**「封面意象与提示词存档」小节**；**未采用的意象也可记一行备选**。
    - **存档小节的固定字段**：候选序号 / 意象名 / 画面要素 / 视觉作用 / 最终采用哪张；另附**统一风格后缀**与**统一约束**（`no text…` + 横构图供 2.35:1 裁切）。
    - **若原始提示词已丢失**（历史上未留档）：允许**据成图反推重建**，但**必须在该节开头显著标注"事后反推重建、非逐字原始 prompt"**，不得让后来者误以为是原样保存。
    - 已摘录的，才可在超期后清理；**未摘录的不清**（宁可多留一轮）。
    - 判断依据：该系列是否已发布/定稿——**未定稿系列的候选图不动**。
    - **✅ 正向做法（治本）**：**生图当下就把提示词写进该系列手册**，不要等到清理时再补——那时原 prompt 多半已丢失，只能反推。
  - **扫描工具（只读，绝不删除）**：`工具脚本/过程文件过期扫描_scan_stale.py`
    - **判龄口径（⛔ 不可改）**：**只看「文件真实最后修改时间」，目录自身的时间一概不看**（目录 mtime 会因子项增删被改写，不代表内容新旧）。
    - 默认：读全部过程类目录，按类给出"保留 x/y 天"或"**超期**"，并汇总可回收体积
    - **⭐ 快照总目录逐项判龄（2026-09-21 修 bug）**：`_备份/` 这类目录的子项**各自是一次独立快照**，**不能按整体判龄**——整体取"内部最新文件"，等于**往里丢一个新快照，整个容器就变年轻**，会把内部早已超期的快照全部藏住（曾实测：容器报 1 天，内部 **17/34 项已 7–19 天**）。脚本已自动识别（名称以 `_备份` 开头，或含 ≥2 个带「公众号文章」层级的子目录），**报告逐快照展开成一行**，`--brief` 也会逐条列出。
      → **教训：凡是"内含多个独立条目"的目录，判龄必须下沉到条目层，不能用整体聚合值。**
    - **`--brief`（定期扫描推荐）**：只列**具体文件夹路径 + 建议动作 + 各类占用**，简洁直观
    - `--out <路径>`：输出 markdown 报告；`--list A`：列出某类完整路径供圈选
    - `--keep-days A=7,B=7,C=14`：临时覆盖默认保留期
  - **⚠️ 汇报纪律（2026-09-11 用户明确）：必须列"具体文件夹名"，不能只说"清理 A 类"** ——类别代号（A/B/C/D）只是内部分级，用户看到"A 类"并不知道要清什么。**任何清理建议都要写出实际路径**（如"建议清理：`青春期30讲\公众号文章\_预览`、`为什么学生不喜欢上学\公众号文章\_预览`"），并同时说明该目录名模式对应什么内容。
  - **例行节奏**：建议**每 1–2 周**跑一次扫描（或用户说"清理一下"时先跑它）；**A/B 类超期即可批清，C 类超期先人工确认是否还有复用价值**（候选图带提示词，删前可把提示词摘进该系列手册）。
  - **仍受 P0 约束**：扫描是只读；**删除一律走回收站 + 分批 ≤10 项 + 逐批核对 + 清后复检**；清理前先 `git commit` 让删除可回滚。
- **产出**：`00_备份与过程文件扫描报告_<日期>.md`（扫描阶段）+ `00_目录清理执行报告_<日期>.md`（执行阶段，含已删清单、保留项、复检结果、可恢复路径、遗留项）。

**第 11 步 · 真实素材池（长期积累，账号最值钱的资产）**

> **账号最核心的辨识度不是"讲了多少本书"，而是"一个也在重启的爸爸，怎样一次次失败、调整、再尝试"。** 完整但虚构的戏剧故事，长期不如一个经确认的真实细节更能建立信任。

- **平时就要积累、不要等到写稿才找**：在`_资产/真实素材池.md`（或按年一份），随手记下**极小**的真实片段，每条只记 6 项：
  1. **当时发生了什么**（场景/时间点，一句话）
  2. **父亲原本说了什么**（原话）
  3. **孩子真实回应了什么**（原话，越朴素越好）
  4. **哪一步没有成功**（关键——失败比成功可信）
  5. **后来只改变了什么**（哪怕只改一个小动作）
  6. **哪些细节不能公开**（隐私红线，写稿时避开）
- **用法**：写新篇时**优先从这里取 1 个真实细节**接进文章；**每篇哪怕只有 1 个经确认的真实细节，也强于全篇虚构**。用过的要**在池里标记"已用于第X篇"**，避免反复消耗同一个细节（呼应"人物连续性表"）。
- **触发时机**：用户随口讲的家事、一次冲突后的复盘、孩子说过的一句有意思的话——当即问一句"这个能写进去吗、有没有不能公开的部分"，确认后入库。
- **边界**：未经用户确认的家事**不入池、不入稿**；入库不等于可发布，**发布前仍需用户当次确认**。

**第 12 步 · 发布后数据复盘闭环（让数据反哺规则，而不是只靠编辑经验）**

> 当前流程擅长"生成并检查"，但**规则主要来自编辑经验，缺少真实发布数据反哺**。所谓"A/B 备选标题"若从不回收数据，就只是准备了两个标题、并未完成验证。

#### 12.1 ⛔ 先分清两级指标（**最容易搞错的一点**）

> **不同层级的指标不能混在一张表里比**——这是本项目已踩过的坑
> （曾把"文章本体 vs 后台卡片"当成封面 A/B 测试、曾用含极端值的偏样本算均值）。

| 级别 | 指标 | 纪律 |
|---|---|---|
| **篇级**（一篇一行） | 阅读、分享、收藏、平均停留、**流量来源构成**、新增关注、推荐量/曝光 | **可做篇间比较**（**但须同载体比**） |
| **账号 / 日期级** | ⭐ **送达人数**、当日通知额度给了谁 | **⚠️ 不可拆给单篇、不可篇间比较**——同一天多篇送达数相同（因通知额度只有一条），**拆算是伪精度** |

#### 12.2 篇级字段表（追加到 `_资产/发布数据复盘.md`，一行一篇）

| 字段 | 说明 | 适用 |
|---|---|---|
| 篇号 / 标题 | 便于回溯 | 全部 |
| ⭐ **载体** | **长文（图文消息）/ 卡片文章（贴图）**——**两载体不可互比** | 全部 |
| ⭐ **流量来源构成** | 会话 / 朋友圈 / 公众号主页 / 搜一搜 / **平台推荐** / 其他（占比或量级） | 全部（**卡片重点看"推荐"**） |
| ⭐ **平均停留** | 后台可得则记；**卡片通常无此项** | 长文重点 |
| ⭐ **通知状态** | 本篇**是否开启了群发通知**（是 / 否 / **未知**）——**"未知"也要如实写，不要猜** | 全部 |
| ⭐ **观察窗口** | 每条记录**必须注明是 24 小时还是 7 天**；同一篇的 24h 与 7d 是**两条独立记录**，不混算 | 全部 |
| **标题类型** | 情绪共鸣型 / 问题解决型 / 认知反差型（对应第 1 步三类） | 全部 |
| **开头类型** | 现场故事 / 问题复盘 / 对话 / 清单 / 概念 / 书信 | 全部 |
| **结构类型** | 对应第 2 步六种结构中的哪一种 | 全部 |
| 阅读 / 分享 / 收藏 | 后台可得的量级数据 | 全部 |
| **推荐量 / 曝光** | 卡片文章的**主要**评价指标 | **卡片** |
| **是否带来关注** | 新增关注数 | 全部 |
| **哪句话被读者反复引用** | 留言/转发语里出现的那句（最直接的"传播金句"证据） | 全部 |
| **读者在哪类内容下更愿留言** | 主观归因，一句即可（**须显式标注"推断"**） | 全部 |

#### 12.3 ⛔ 两条硬约束

1. **长文与卡片文章的阅读量不可互相比较**（渠道机制不同，见 13-card 8.3）——
   **卡片看推荐量/曝光，长文看停留/分享/评论/新增关注**；互动低是**卡片渠道属性**，不等于没价值。
2. **数据 / 推断必须分开写**（呼应错误案例 D3）——后台没有的数字**不填、不反推成"数据"**；
   反推结论须标 **⚠️ 反推** 与**待确认**（如"是否占通知额度"至今仍是反推，见 13-card 8.2）。
- **真正的 A/B**：同一篇的两个备选标题**分发到不同渠道或不同时段**并记录差异，才叫验证；只在字段表里列两个标题不算。
- **决策门槛：连续积累 20–30 篇之后**，再据此调整**篇幅、标题结构、发布时间、系列长度**——不要凭几篇的体感就改规则。
- **反哺 SOP**：数据结论若稳定成立（如"问题解决型标题的分享率持续更高"），**把结论写回第 1/2 步的规则**，让经验升级为证据。
