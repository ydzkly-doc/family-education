# 卡片文章（贴图）· 总纲与索引

## 零、地位与适用范围

### 0.1 它管什么

**每篇公众号长文，额外产出一个「卡片版本」**（微信官方形态名：**贴图**，俗称"小绿书"）。

| 项 | 说明 |
|---|---|
| **适用** | 所有系列、所有长文（**存量补做 / 新生成同办**） |
| **不适用** | 长文本身的写作与排版（仍走原 SOP 第 0–9 步） |
| **触发点** | **第 9.5 步**（长文第 9 步自检之后）；**长文是唯一素材来源** |

### 0.2 与长文的关系（一句话）

> **长文是「深度内容」，卡片文章是「轻量分发形态」，两者共享同一份素材、不同的组织方式。**

- 长文：吃**订阅关系**，触达 ≈ 粉丝数 + 社交转发；
- 卡片文章：吃**算法关系**，**不看粉丝数**，**优先推给非粉丝**；
- 卡片文章底部**自动带原文链接** → 陌生人刷到卡片 → 点进长文 → 关注沉淀。

### 0.3 三档优先级如何接入

| 档 | 卡片文章里包含哪些 |
|---|---|
| **P0 · 红线** | ①平台规格不违背 ②**卡图不印声明**（**2026-09-29 用户改定**：课程来源／改编／人物示意一律**不印在卡图**，卡图只留**署名·篇号·卡序**；声明移入**长文正文与后台描述**，来源类型改为**逐卡内部回溯记录**——见 `14-card-writing.md` 2.6）③不杜撰（回溯长文）④不加动作指令/不绝对化 ⑤不标原创/不填作者 ⑥Gate A/B |
| **P1 · 质量线** | 张数控制、封面卡抓眼球、内容卡信息完整、三件交付物齐备、体积/比例合规、自检通过 |
| **P2 · 偏好** | 配色、底图意象、话题标签数量 |

**已知冲突的既定裁决**：
- **内容完整 vs 张数少** → **两者都要**：张数取"内容够用的最小值"（**3–5 张**），靠**每张内容做厚**解决；
  **不为凑数加卡，也不为省事压卡**（判定法见 `14-card-writing.md` 1.3）。
- **体积小 vs 画质** → **柔化底图**解决（文字是后画的，不受影响）。
- **封面卡抓眼球 vs 声明可见** → **2026-09-29 改定：卡图不再印任何声明**，此冲突**自然消解**；完整声明仍在长文正文与后台描述中，封面只需保证**主文案与署名**落在 16:9 安全区内。

## 一、形态定义

```
卡片文章 = 封面卡 × 1 + 内容卡 × N + 收尾卡 × 1
         + 卡片正文（纯文本，含话题标签）
         + 字段表（标题 / 无作者 / 描述指引 / 标签）

N = 长文的独立核心意思数（1–3），总张数 3–5 张
```

> **⭐ N 是"数出来的"，不是"定死的"**——先数长文有几个独立核心意思，再定 N。
> **权威规则与判定法见 `14-card-writing.md` 第 1.3 节**（含"3 张何时是正解""何时该合并"）。
> 本文件只记平台规格与流程，**不重复张数判定法**。

### 1.1 三条禁令

| ⛔ | 说明 |
|---|---|
| **不是**"把长文拆成几张图" | 要**重新组织叙事节奏**，按"一屏一段"重新分屏 |
| **不是**"长文摘要截屏" | 卡片图是**重新排版的文字卡**，不是正文截图 |
| **不是**"长文的缩略版" | 它是**独立成型**的内容，单看卡片也能读懂 |

### 1.2 平台机制（为什么要做）

| 机制 | 依据 |
|---|---|
| 贴图走**算法推荐**，**优先推给非粉丝** | 后台提示语："发布后优先推荐给非粉丝用户，触达更多新读者" |
| 官方力推：一年 1.16 亿篇、同比涨 377%；近一月活跃号 52% 用过 | 微信《公众号14周年创作者报告》2026-08-17 |
| **粉丝少 + 内容大众向的号最受益** | 行业双号实测：专业深度内容/大粉丝号效果不明显 |

> **系统的自动生成版封面难看、描述被截、无标签** → **必须自做才能拿到流量**。

## 二、⭐ 平台规格（官方口径 · 不可违背）

> **纪律**：标 ✅**官方** 的**不得凭印象改写**；标 ⚠️**实测 / 反推** 的可作依据但**不得当平台承诺**；标 🔶**待确认** 的**不得写入结论**。

> **⚠️ 元规则 · 平台规格带时效（易被当成永久事实，务必先读）**
> 微信贴图的**尺寸、字段、推荐机制、通知规则都可能变**——本节的结论**是某一时点的快照，不是永久事实**。
> **每次做卡片文章前，至少抽查三项**：图片张数上限 / 展示比例 / **是否占通知额度**；
> **以当前官方文档（developers.weixin.qq.com）+ 后台实际显示为准**。
> 若官方页面无法访问（如网络原因），**该项降级为 🔶待确认**，并在交付说明里写明"未复核"。

| 项 | 规格 | 强度 |
|---|---|---|
| **正文格式** | **仅纯文本** + 部分特殊功能标签（如商品） | ✅ **官方** |
| **标题上限** | **32 字** | ✅ **官方** |
| **图片张数** | 最多 **20 张**（首张即封面图） | ✅ **官方** |
| **展示比例** | **3:4**（最佳展示尺寸） | ✅ **官方** |
| **封面展示比例** | **16:9**（可选 1:1 / 2.35:1） | ✅ **官方** |
| **作者字段** | **无**（newspic 结构无 author） | ✅ **官方** |
| **能否标原创** | **不能** | ✅ 多源一致 |
| **描述字数** | **540–660 字**（钩子型，**600 为中心 ±10%**）；硬上限 **1064**（含换行符） | ⭐**2026-09-29 用户改定**（以微信自动生成贴图正文的 600 字为**中心**，下限由 200 提到 540）；见 `14-card-writing.md` 2.2.2 |
| **是否占用群发通知额度** | **⚠️ 反推：可能占用**（同日多篇送达数相同、文章本体送达为 0）；**待后台确认** | ⚠️ **项目数据反推**（**非**实测确认） |
| **必须勾"允许被推荐"** | 否则**公域入口锁死** | ✅ 多源一致 |

### 2.1 ⛔ 最重要的一条（官方原文）

> **「图片消息则仅支持纯文本和部分特殊功能标签如商品」**（对照图文消息：「**支持HTML标签**」）

| 能力 | 长文（news） | **贴图（newspic）** |
|---|---|---|
| 加粗 / 斜体 / 下划线 | ✅ | ❌ |
| 字号 / 颜色 / 背景色 | ✅ | ❌ |
| `<section>` / `<p>` 等标签 | ✅ | ❌ 会当纯文本或过滤 |
| `<img>` 插图 | ✅ | ❌（图只能走卡片图列表） |
| **分段** | HTML 控制 | **靠空行** |
| emoji / 符号 | ✅ | ✅ ⚠️ **仅限描述字段** |
| 超链接（小程序 / 网站） | ✅ | ✅ |

> **⚠️⚠️ 上面这行"符号 ✅"只适用于描述（`content`）字段——不要误推到卡片图！**
> **两层完全不同**：
> - **描述字段**：微信客户端渲染 → emoji、符号**正常显示**。
> - **卡片图上的文字**：由**本工坊用 PIL + 中文字体（微软雅黑）绘制** →
>   **字体不含的符号会变成空心方框（豆腐块）**（✔✕✓✗ 全在此列）。
> **→ 卡片图文案里的任何非中文符号，必须先验字形**（见 `15-card-visual.md` 5.3）。

> **⛔ 纪律**：本工坊的《微信公众号排版HTML规范》（section 流式、零 `data-*`、标签白名单）
> **只适用于长文正文**，**对卡片正文完全不适用**。

### 2.2 ⚠️ 封面按 16:9 展示 → 必须设安全区

首图作封面时按 **16:9 中心裁切**展示，而卡片本身是 3:4 → **裁切带只占卡片中间约 42%**。

```
1242×1656 卡片 → 16:9 裁切带 = y 478 ~ 1177（高 698px）
```

**→ 封面卡的所有关键内容（主文案、署名）必须落在该带内。**
（⚠️ 2026-09-29 起**卡图不再印来源／改编／示意声明**，安全区只服务主文案与署名；不再有“标注要落进安全区”这一项。）

**自检断言（必须写进脚本）**：
```python
y0, y1 = int((H - W*9/16)/2), int((H + W*9/16)/2)   # 478, 1177
assert 所有文字块 b[1] >= y0 and b[3] <= y1          # 仅封面卡强制
```

### 2.3 两套规格别混

| 用途 | 比例 | 体积 |
|---|---|---|
| **长文封面**（原有） | **2.35:1**（1200×511） | ≤200KB |
| **卡片图**（本细则） | **3:4**（1242×1656） | **<100KB** |
| 卡片图**作贴图封面时** | 系统按 **16:9** 裁切展示 | **需设 16:9 安全区** |

## 三、⭐ 三件交付物（职责边界 · 硬规定）

| 文件 | 放什么 | **⛔ 不放什么** |
|---|---|---|
| `01_标题作者摘要.txt` | **后台要填的字段** + 卡片顺序 + 来源声明 + 回溯对照 + 发布清单 + 差异对照 + ⭐**朋友圈转发文案**（见下） | **不放正文全文**（避免两处不同步） |

| `第XX篇_卡片_NN_*.jpg` | 卡图，**文件名即顺序**（两位序号）｜**必须带篇号前缀** | — |

### 3.0 卡片 `01` 字段表里的「朋友圈转发文案」

**卡片发布包的 `01` 同样含该段**（卡片天然是朋友圈素材）。规格同 `05-publish-kit.md`。
⚠️ 别与**卡片描述**混：描述是给读者讲内容（`02` → 后台，540–660 字），
朋友圈文案是给号主表达立场（`01` → 发朋友圈时配字，一屏内）。**两者不得互相复制。**

### 3.1 命名与目录

```
<系列资产码>_<中文系列短名>_第XX篇_卡片_NN_<角色>_vNN.jpg
01_标题作者摘要.txt
02_卡片正文（纯文本）.txt
```

> ⛔ **全局唯一文件名是硬要求**。本地目录名上传后不会进入公众号素材库，只有篇号仍会跨系列重名；因此必须同时包含系列资产码、篇号、卡序、角色和版本。系列资产码在 Gate A 前登记，4–12 位大写英文字母或数字且以字母开头，同一系列永久固定、不得复用；角色只用“封面 / 内容 / 收尾”。任何像素、文字或来源标注变化都递增版本号。示例：`HZYJSJ_孩子与手机_第01篇_卡片_01_封面_v01.jpg`。正式包、上传清单和素材库使用同一 basename；预览副本带 `_预览` 并与上传目录隔离。底图、渲染配置和待验收区资产也带系列码、篇号和版本，防止共享目录覆盖。

```
公众号/<系列>/公众号文章/发布包_第X篇_xxx/
├── 长图文发布包/           ← 长文三件套（正文.html / 01字段 / 封面.jpg）
└── 卡片发布包/             ← 卡片交付物（01字段 / 02正文 / 第XX篇_卡片_NN.jpg）
```

**⚠️ 目录迁移前必做**：改造 3 个工具脚本，否则自检链路全断。

| 脚本 | 现状假设 | 需改造为 |
|---|---|---|
| 系列发布全套自检 | `发布包_*` 下**直接**找文件 | 优先查 `长图文发布包/`，**回退**包根 |
| 重建全部正文预览 | 同上 | 同上 |
| 模板感诊断 | 同上 | 同上 |

**兼容策略**：加一个"解析内容目录"辅助函数——**子目录存在则用之，否则回退包根**。

### 3.2 ⭐ 目录迁移时机（**策略：逐篇随做**，2026-09-15 用户确认）

> **规则：做某篇的卡片文章时，顺手把该篇的发布包迁为新结构。**

| 情形 | 做法 |
|---|---|
| **本篇要新做卡片文章** | 建 `卡片发布包/` 的同时，把已存在的长文三件套移入 `长图文发布包/` |
| **旧系列、暂不做卡片** | **保持旧结构不动**（工具链兼容，照常可用） |
| **新系列 / 新建发布包** | **直接用新结构**（一步到位，无需迁移） |

**⭐ 关键区分**：**目录迁移 = 移动文件位置，不修改内容**。
→ **不违反"存量补做时只读长文不改"的纪律**（那条禁止的是**改长文内容**，不是禁止移动文件）。

**⚠️ 迁移三步（顺序不可颠倒）**：
1. **先改造 3 个工具脚本**（见上表）——**必须在移动文件之前**，否则自检链路全断；
2. 建两个子目录，移入文件；
3. **跑全套自检 + 预览重建验证**（确认 `wx_html_fix` 合格数不变、预览篇数不变）。

**⚠️ 迁移时要同步检查的两处判据**（易漏，2026-09-15 踩过）：
- **「发布包卫生」白名单正则**必须含 `长图文发布包` 与 `卡片发布包`；
  否则这两个子目录会被误判为"多余待清理"甚至误删（详见 `08-selfcheck.md`）。
- **`.gitignore` 不应误伤**子目录内的交付物（子目录名不含 `_` 前缀，正常不会被忽略规则命中）。

## 四、⭐ 标准工作流（12 步 · **含两道强制关卡**）

> **前置条件**：**长文已完成**。卡片文章**不先于长文**——长文是唯一素材源。

### 4.0 ⛔ 最重要的一条：**先出设计文档，等确认，才能动手**

> **生成卡片文章是一个「分阶段」的过程，不是一次做完。**
> **第 0–3 步只产出「设计文档」，交付后必须停手等用户确认；确认之前，禁止执行第 5 步及以后的任何动作。**

| 阶段 | 步 | 产出 | 是否停手 |
|---|---|---|---|
| **① 设计阶段** | 0–3 | **设计文档**（拆卡表 + 正文草稿 + 字段草案 + 素材回溯） | — |
| **⏸ Gate A** | 4 | 把设计文档交付用户确认 | **⛔ 必须停手** |
| **② 制作阶段** | 5–9 | 底图 + 全部卡（3–5 张） | — |
| **⏸ Gate B** | 10 | 首张封面卡交付确认（首次做 / 换风格时） | **⛔ 必须停手** |
| **③ 组装阶段** | 11–12 | 完整发布包 + 自检报告 | — |

**⛔ Gate A 未确认前，明令禁止**（逐条照办，不得以"先做了再说"绕过）：
1. **禁止生成任何底图**（消耗积分、且方向可能白做）；
2. **禁止渲染任何卡片**（含试渲、样张）；
3. **禁止创建 `卡片发布包/` 目录或任何占位文件**；
4. **禁止做目录迁移**（迁移与卡片制作是一个动作，等确认后一起做）；
5. **禁止跑底图后处理脚本**。

**允许做的事**：只有**只读的核对计算**（如正文字数核对、标签数核对、素材段号回溯）。

### 4.2 ⭐ 设计文档必备内容（Gate A 交付物）

设计文档**必须是独立文件**（如 `00_第X篇拆卡方案_GateA.md`），且**必须含下列 7 项**：

| # | 内容 | 说明 |
|---|---|---|
| 1 | **素材清单** | 逐条标出**长文段号** → 场景/机制/金句（证明不杜撰） |
| 2 | **拆卡表** | 每张卡：主题标签 + 主标题 + 文案草稿 + 内容量<br>⭐ **并写明张数依据**："长文有 X 个独立核心意思 ①…②…；故 N=X，共 X+2 张"，**并说明为何某些意思不合并 / 某些已合并**（见 `14-card-writing.md` 1.3） |
| 3 | **取舍说明** | **砍掉了哪些素材、为什么**（不是只列用了什么） |
| 4 | **描述全文 + 与卡图的「重复度对照」** | 纯文本草稿（**钩子型 540–660 字**）+ 字数核算（用 `卡片正文字数核算_check.py`）+ **标出"卡片已讲/描述只讲没讲的"** + **末段有自然引导原文的句子**；⚠️ **若描述扩写过，必须"扩写后重做一次对照"**（见 `14-card-writing.md` 2.2.2） |
| 5 | **字段草案** | 主标题 + 备选 + 标签 |
| 6 | **⚠️ 数字一致性核对** | 卡片文案里的数字/引语**与长文正文逐项比对**（防与长文摘要或印象不一致） |
| 7 | **⭐ 逐卡内部来源回溯表** | 每张卡：来源段号 → **内容类型（真实/改编/他人）** → **内部记录文字**（真实经历记「真实经历 · 已确认」，⛔ 不得记为“改编”）；⚠️ 同篇内可并存不同类型；**⚠️ 2026-09-29 起本表只进内部，⛔ 不印卡图** |

> **为什么第 6 项重要**：本项目**实测发现过长文字段表摘要与长文正文数字打架**
> （摘要写"讲八遍"、正文写"讲了两遍"）。**卡片一律以长文正文为准**。

### 4.2.1 ⭐ 规则演进**不追溯存量**（2026-09-17 用户明确）

- **新规则只对后续篇目生效**；**已生成的卡片文章保持不变**，不因规则更新而返工。
- 存量与新规则冲突时**默认不动**，**除非用户当次明确点名要求返工**。
- **复核存量只用于"发现规则问题"，不用于"判定存量不合格"**——
  例如 2026-09-17 用新的张数判定法复核五篇，发现第 1 篇三卡厚薄雷同，
  该观察**仅作规则改进依据，不作为返工依据**（五篇均未违反硬约束）。

### 4.2.2 ⛔ 复核存量的三条纪律（2026-09-17 实修，都是真实误报换来的）

> **背景**：复核「儿童情绪管理」5 篇时，我连发 **3 次误报**，
> 全部源于"急着跑检查、没想清楚判据"。**复核存量比复核新稿更容易出错**——
> 因为它套着两套标准（当时的 / 现在的），还夹着自己的假设。

| # | 纪律 | 反面案例（真实） |
|---|---|---|
| **1** | **先用"当时的标准"判是否合规**，再谈"对新标准如何" | ⛔ 拿新标准（描述 200–600，2026-09-17 起；后于 2026-09-29 再调为 540–660）去量按更早标准（200–350）做的稿，说“在下限附近”——**而它们按当时的标准 5/5 全合规** |
| **2** | **判据要先想清"什么才算真问题"，再设计匹配方式** | ⛔ 用「12 字精确前缀」判"卡片照抄长文" → **5 篇全红**。但**卡片本就该是改写压缩**，逐字匹配必然全红。**改用「最长公共子串 ≥14 字」后，真问题只有 2 处** |
| **3** | **语义类检查必须"真读一遍"，不能只跑指标** | ⛔ 判"描述缺引导原文"只查**最后一段** → 报 4 篇缺；**实际引导句写在第 2 段，5/5 都有**。另把「**不是**永远不发火」误判为绝对化（**否定式恰是反绝对化**） |

**⭐ 元规则**：
- **机械匹配只能做"筛子"，不能做"判官"**——命中后**必须人工回读原文确认**；
- **黑名单/匹配词越短越误报**（同"用亮度找水印必误报"）——取"能唯一指代"的完整形式；
- **复核报告要先写"我用了什么判据"，再写结论**——判据错了，结论全错，且**看起来很像在认真检查**。

**复核内容层时的最低清单**（不能只看规格）：
① 卡面**有无声明残留** vs 长文类型声明（2026-09-29 起卡面应**零声明**） ② 卡面有无动作指令/绝对化 ③ 正文与卡面的**长句级**重复
④ 正文有无"元叙述"导语（"这些卡片…/卡片把…"）⑤ 人设连续性 ⑥ 敏感议题边界。

### 4.3 关卡纪律（**与主机 Gate 1/2/3 同等效力**）

- 只认用户**当次、明确、点名到这一步**的指令（"确认/OK/开工/按这个做/可以了"）；
- **⛔ "继续做 / 你定就行 / 一次做完 / 接着弄" 等概括说法，不得扩大解释为对未提及关卡的授权**；
- 用户说"看看 / 参考一下 / 还有吗"**不算确认**；模糊或未点名时，**停在关卡、等待**；
- **"少交付"≠"少确认"**——减少 present_files 频率**绝不等于**可以减少关卡确认；
- **不得因"这是增量功能"而放宽关卡**。

### 4.4 存量 vs 新生成（**两个入口，同一套规则**）

> ⭐ **核心不变式**：**无论哪种入口，长文都是唯一素材源，且卡片文章都在长文完成后做。**

| 入口 | 场景 | 流程差异 |
|---|---|---|
| **A · 存量补做** | 已有长文（含已发布的） | 直接从**第 0 步读长文**开始 |
| **B · 新生成** | 新系列 / 新篇 | 长文走完原 SOP 0–9 步 → 再进第 0 步 |

**两入口只有 3 处差异**（起点 / 长文状态 / 图片素材），**其余规格、张数、文案规则、关卡、自检完全一致**。

**⚠️ 存量补做的三条额外纪律**：
1. **⛔ 只读长文，绝不回改**（长文可能已发布，改动会造成线上线下不一致）；
2. **⛔ 不改长文标题去迁就卡片**（卡片标题可另起，不得反向修改长文）；
3. **可回溯对照以"已定稿长文"为准**。

**批量补做的排序建议**：数据表现好的 → 主题大众向、痛点明确 → 总纲/导航型 → 其余按系列顺序。

### 5.A · 平台规则类（来源：未先查官方文档就动手）

| **A7** | 不知"**张数越多越掉量**" → 设计了 8 张 | **3–5 张**（按内容厚度定） | **"上限"≠"该用多少"** |

> **⛔ 元规则：动手设计前，先查官方文档（developers.weixin.qq.com）+ 平台实测。**

### 5.B · 交付物类

| # | 错误 | 正确做法 | 教训 |
|---|---|---|---|
| **B1** | 字段表里**存了两处正文** | 字段表**只放后台要填的字段** | **单一真相源** |

### 5.C · 技术类 → 详见 `15-card-visual.md`

| **C12** | ⭐⭐ **字数用「去空白」口径算** → **漏算全部换行符**，报 983 而实际 1035，**已超限而不自知** | 一律用 `卡片正文字数核算_check.py`（**后台口径：标题+content，换行算 1 字符**）；CRLF 先归一 | **口径不对，越算越错**；数字必须与后台能对上（拿后台显示值校准） |
| **C18** | ⭐⭐⭐ **用「图像法」验文字位置**（行亮度方差 / 颜色匹配找文字）→ **底图卡上必然误报**：暗化后的底部暖光与浅色文字色值接近，6 张封面卡被误报 5 张"出 16:9 安全区" | **读渲染器记录的 `BOXES` 文字框**（白盒判据）——渲染时本就用它做断言；实测 6/6 在带内 | **判据可靠性：白盒记录 > 图像实测 > 人工目测**；与 C5（亮度找水印必误报）同类，见 `15-card-visual.md` 十 |
| **C19** | ⭐⭐⭐ **内容密度超标** → 根因不是版式，而是**执行时偏离 Gate A 拆卡表**（自加节点 / 自带说明行 / **照搬长文段落**）。**已连发 4 次**：80%/75% → 75% → 73%×4 → **81.5%/70.8%/79.2%** | **Gate A 拆卡表＝施工图**，照抄节点数与段落数；**渲染前先跑密度预估脚本**（目标带 **62–68%**，红线 **70%**；行距 1.66 下，主标题 2 行的卡正文 **9–10 行**）；想加内容先改设计重过 Gate A；别靠目检（80% 时肉眼反而觉得"信息量足"） | 见 `15-card-visual.md` 十一 / 11.1 |
| **C20** | ⭐⭐ **内容卡体积压不进 100KB**（q=30 仍 101–107KB）→ 直觉想**柔化底图**，但**内容卡是纯色底，柔化几乎无效**——真因是**文字太多撑满画面** | **先量密度**，再考虑画质手段；**内容卡体积几乎全由文字区面积决定** → **压体积的正解是减内容，不是降质量**（精减后 q 反而从 30 升到 39–57） | 见 `15-card-visual.md` 11.1 |
| **C21** | ⭐⭐ **把"不超限"当目标** → 密度**每张都压到 64–65%**（9 张里 4 张正好 64.0%），**看似合规、实则零余量**，改一处就破线 | **规则要给"目标带"而非只给"上限"**：目标带 **62–68%**、红线 **70%**；**按行数控**（主标题 2 行的卡正文 9–10 行） | **与 C11 同源**（贴着上限写＝把风险留给自己）；见 `15-card-visual.md` 11.2 |
| **C22** | ⭐⭐ **复核存量时"核过"≠"核到位"**：①只用自写 `len()` 数描述，**没跑规定工具**（且标题正则漏匹配一篇）；②只判"是否落在 200–600 区间（2026-09-17 当时标准；2026-09-29 起为 540–660）"，**没判"是否该按 600 写满"**——5 篇全部停在旧标准 350 的天花板（333–350），距新上限尚有 250+ 字余量 | 复核**必须用 SOP 规定的工具**（不自己造口径）；判据要**逐项确认两端**——既看"有没有超上限"，也看"离上限多远、是否该写满" | **"落在区间内"是最懒的合规判定**，它掩盖"下限贴着旧标准"这类问题 |
| **C23** | ⭐⭐ **把"留白"当成可独立调的参数** → 用户说"上下留白太多"，我第一反应是"删文字"；实际**留白是密度的果**：`留白 = 可用区×(1−密度)`，**压留白不降密度、反而升密度** | **只规定"密度目标带"，不给"留白数值"**；要说留白，必须先说明它是**该密度下的自然结果**（62–68% ↔ 上下各 225–265px） | **因果搞反＝开错药**：本系列真问题是"内容量离散（109–233字，跨2.1倍）"，不是"留白太多" |
