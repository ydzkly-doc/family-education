## 【根因实证】data-page-node-id 不是秀米/用户注入，是 present_files 预览面板写回磁盘！
- 用户坚称从未手动改过文件、不知秀米为何物。做对照实验坐实根因：
  1. cp 一份干净正文为 _probe_test.html（data-id=0，16912字节）；
  2. 用 present_files 打开它（预览面板渲染）；
  3. 6秒后读回磁盘：文件变 22072 字节、mtime 更新、被注入 data-page-node-id（每个 DOM 节点一个22位随机串，连 head/meta/title/body 都打）。
- **结论：present_files 的内置 HTML 预览面板在渲染时会给每个节点打 data-page-node-id，并把渲染后的 DOM 写回磁盘源文件。** 被实际渲染/对焦的文件才被污染（预览默认渲染焦点文件，故一次 present 里通常1-2篇中招）。
- 这解释了历史：第3篇 290 个、第6篇 174 个，以及备份目录里"修复后含dataid备份"全是同一来源，**与用户无关、与秀米无关**。之前归因为"秀米往返注入"是错的，已向用户更正。
- **规避/根治（以后强制）**：
  ① present_files 展示正文后，交付/发布前**必须重跑 `wx_html_fix.py --check`（或无参修复）剥 data-***，因为预览会再次污染；
  ② 更稳的做法：**预览只打开合并预览页 `_全部正文预览_N篇.html`**（它是衍生文件、不发布、可随时由 _build_preview.py 重建，被污染也无所谓），**不要把各发布包的正式正文 HTML 直接 present_files**，源文件就不会被写回污染；
  ③ 每次生成/修改正文后、且在任何 present_files 之后，跑一遍校验确认 data-*=0 再交付。

## 【根治方案】data-page-node-id 预览污染 —— 预览副本隔离机制（已验证闭环）
- 补充实证：预览面板**只渲染 .html 并写回污染；.txt 不进富文本渲染、不被写回**（探针对照：.html 被注入、.txt data-id 恒0）。
- 根治做法（断舍离系列已落地，以后所有系列照此）：
  1. **预览只读副本**：`_build_preview.py` 读取发布包【源正文】时先正则剥 `data-*`（双保险），合并预览页输出到独立 `_预览/` 目录；该目录纯派生、不发布、随时 `python _build_preview.py` 重建，被面板注入也无所谓（下次重建覆盖）。
  2. **源文件不进预览**：present_files **只打开 `_预览/` 里的合并副本**，绝不再把各发布包的正式正文 .html 直接送预览 → 源文件物理上不被写回。
  3. **发布前保险**：脚本支持 `--fix`，就地剥除所有发布包源正文的 data-*；交付/发布前跑一次。
- 已验证：预览后源6篇 data-id 恒0；重跑脚本副本一键复原0、源不动。旧的根目录预览页已删除，统一收进 `_预览/`。
