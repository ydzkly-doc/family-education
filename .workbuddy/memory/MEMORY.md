## 一、内容质量总纲（最高优先级，覆盖一切排版规范）

**0. ⭐ 五层完整性红线（先于一切节流指标）**：判断标准不是"有没有重复"，而是"删完以后场景、心理转折、机制、方法、边界是否仍然完整"。
- ① **场景**（道理长在哪个具体瞬间：时间/动作/对话/物件）② **父母心理转折**（我怎么从旧想法走到新想法）③ **机制**（为什么会这样）④ **方法**（今晚能做什么：具体话术/动作/时机）⑤ **边界**（适用到什么程度、何时找专业帮助）
- **自查顺序固定：先保五层齐全 → 再压重复句**；节流伤到五层宁可不改；重复句优先"换说法"而非整段删。
- **脚本指标全绿 ≠ 文章完整**，五层必须人工逐篇回答。"结构稿"未达厚度不得称"可发布成稿"；补内容只能用已确认素材（真实细节/标注改编情境/课程案例/机制/边界），禁重复金句、同义改写、无据结论、新编事件凑篇幅。

**1. 叙事真实性三分法（最高门槛）**：① 用户确认的真实经历 → 可写"我和儿子"；② 课程案例/改编情节 → **开头第一屏就标注"家庭场景改编"**，避免强纪实语气；③ 他人案例 → "一位父亲"/"课程中有个家庭"，**绝不转换成作者本人**。**红线：绝不把讲师自述改写成"我"的经历。**

**2. 人物连续性**：孩子固定 **15 岁 / 高一 / 儿子**；署名"一个也在重启的爸爸"；后台【作者】字段用账号名"归途有光·和孩子一起重启"。

**3. 打破模板感——结构必须轮换**：**6 种结构**轮换使用——现场故事型 / 问题复盘型 / 对话拆解型 / 清单工具型 / 读书概念解释型 / 一封信或自问自答型。单篇"不是…而是…"≤2 次、"那一刻/忽然/慢慢/一点点"合计≤3 次、"愿你…"不要每篇都用。"我后来试着做的几件小事"**只在真正的方法文里出现**。
- **相邻篇语言指纹（比累计统计更严）**：判定单位是"相邻"——相邻两篇不连续用同类顿悟转折、不连续用同一种祝愿收尾、不连续复制同式标题。各出现 3 次但分布均匀 > 集中在前 3 篇。
- **不强制装配件**：金句块/"三件事"/完整系列地图/下篇预告都是**可选零件**——金句只有真从场景长出来才做；系列地图只在首篇/末篇/总导航篇。
- **篇幅（以中文可见字符计）**：普通完整稿 **1600–2400**（轻稿 1600–1900 / 深度稿 1900–2400），速览短答 **900–1400**。区间是"报警器"不是配额。**删改降幅 ≥30% 必须额外复核**叙事张力、情绪承接、方法细度、阅读节奏。
- **⭐ 动笔前先数素材（2026-09-10 新增，已入 SOP）**：起笔前先列素材清单——真实/改编细节 ≥2、机制 ≥1、可照念台词 ≥1、边界 ≥1、场景起点；五项≈900–1100 字，加过渡正常落到 1600–1900。**撑不到下限先回原文补素材，不写完硬凑**；写完偏薄回补"哪一层没写足"，不从句子数量补。
- 工具：`python 工具脚本/模板感诊断_template_scan.py --dir "<系列>/公众号文章"`（+`--count` 字数区间 / `--diag-structure` 结构轮换 / `--baseline` 算降幅）。**改造/新写系列先跑它定位，改完跑到命中下降。**
  - 阈值已修（2026-09-10）：**1400–1600 判"偏薄（未达普通稿下限）"**，此前该区间被误判为"正常"。

**4. 标题去同质化**：系列内轮换三类——情绪共鸣型（≤1/3）/ 问题解决型 / 认知反差型。**禁用无依据夸张**（"90%的父母""一招管住""彻底改变""治好了"）。**1 主 2 备每个都要正文兑现、事实站得住**（备选用户可能真拿去发）。

**5. 系列规模与去重**：普通系列 **3–5 篇**；每篇独立成立；选题前**跨系列去重**（青春期/手机/厌学/学习动力/沟通/犯错 重叠多）；长课程不必篇篇转化；用 1 篇"总导航"承接。

**6. 事实核验与边界（发布前必过）**：故事标明真实或改编；书中模型写"书中提出"、课程观点写"课程认为"；研究/数字/销量/履历**发布前核验来源，核不到不写**；经验归纳写"常见的三种情况"，不写"只有三种""必然导致"；**厌学/自伤/饮食障碍/长期失眠等必须加专业求助边界**。

**7. 真实素材池**：`_资产/真实素材池.md`——记6项：当时发生了什么 / 父亲原本说了什么 / 孩子真实回应了什么 / 哪一步没成功 / 后来只改变了什么 / 哪些细节不能公开。每篇接进 ≥1 个确认过的真实细节强于全篇虚构；用过的标"已用于第X篇"。

**8. 数据复盘闭环**：`_资产/发布数据复盘.md`——每篇发布后记：标题类型/开头类型/结构类型/阅读分享收藏/是否带来关注/被引用那句话/24h与7天表现。**真正 A/B = 两个备选标题分发到不同渠道或时段对比**。积累 20–30 篇后再调参数，结论回写 SOP。

**9. 账号级视觉识别**：**不再为每个新系列发明新颜色**——固定 **1 个账号主色 + 2–3 个主题副色**；固定视觉语言"**暖光 / 近景 / 留白 / 物件语言**"；封面走**无人物静物构图**。

**流程弹性（用户特别强调，2026-09-10 二次澄清后收紧）**：关卡是为了不让 Agent 替用户做决定，**不是每步都必须停**。关卡前多给选项、多问一句；信息不足优先问而非假设；局部修改只做要求的部分；**主动暴露不确定性**（事实不清/数字存疑时在 Gate 里提问，不自行圆过去）。
- **⚠️ 但"弹性"只作用于"不必每步都停"，绝不作用于"可以跳过 Gate 3 / Gate 2 / Gate 1 的确认"**。用户说"你定就行/继续做"时，**授权范围仅限用户当次点名的那一步**；不得推及未提及的关卡（用户 2026-09-10 明确纠正："还是要等待我确认……需要我会明确给你指令"）。**减少 present_files ≠ 减少确认。**

## 三、排版与 HTML 规范

**结构铁律**：布局一律 `<section>` 流式，**禁 `<table>` 做布局**（微信安卓 X5 会把 table 宽度固化、窄屏右裁）。
- 每块 `<section style="box-sizing:border-box;width:100%;…">`；卡片靠 background/padding/border-radius/border-left；**禁容器级固定宽、禁 align="center" 居中嵌套**；竖条小标题用 `border-left:5px solid 主色`。
- 标签白名单：`section/p/span/b/strong/br`；**禁 div/h1-4/ul/li/img/data-*/class/`<style>` 块**。
- 文字颜色写在 `<p>/<span>/<b>/<strong>` 自身，`<td>/<section>` 只放 background/padding/width/border。
- **白字大标题**：一行一个独立 `<p style="color:#fff;text-align:center;display:block;">`，**禁 `<br>` 拆行**。正文段落左对齐；仅标题块/金句块/陪伴卡/诗句居中。
- 标准骨架：标题色块（坐标小字+主标题+「第X篇·共N篇|主题」）→ 改编声明（第一屏）→ 开场叙事 → 台词卡（暖色）→ 竖条小标题×N → 正文段 → 方法卡 → 金句居中块 → 边界 → 陪伴卡（灰底、**无动作指令**）→ 来源声明（米白 `#faf9f6`+灰字 `#9a9890`，左对齐）。

**微信丢样式三根因（处理顺序 A→C→B）**：**A** data-* 残留（外部编辑器注入，微信整段重置）→ 删全部 data-*；**C** div/h 骨架 + 白字标题 br 拆行 → 改 p、拆 br；**B** 颜色挂 td/section → color 下沉到 p/span。**一键工具**：`工具脚本/微信HTML规范校验修复_wx_html_fix.py`（`--check` 体检 / 无参修复，幂等）。**交付铁律：全部正文 `合格 N/N`。**

**色板**（篇内统一、系列间有家族感）：学习认知类主色墨蓝绿 `#3f6f6a`/深 `#2f5753`/浅底 `#f0f5f4`；情感治愈类主色莫兰迪赤陶棕 `#b06a48`/深 `#8a4f33`/浅底 `#faf3ec`；长系列按季分色（暖陶橘 `#c0764f` / 雾蓝绿 `#5f8a86` / 暖金棕 `#c0924f`）。台词·方法卡暖琥珀 `#d9963f`/深字 `#b4730f`/底 `#fef6ec`；正文 `#3a322c`。**忌高饱和原色铺屏**；一页强调色 ≤2 个色系。

**封面**：正文全做完再做；先出 1 篇 2–3 张候选确认风格再批量；**优先无人物静物构图**；后处理 Pillow 裁 2.35:1 中央宽幅带（水印位于 x>1216·y>894，底部裁到 ≤894）→ 压 ≤200KB。

## 七、交付与确认纪律（2026-09-10 用户明确，跨系列通用）

**这是两件必须分开的事，切勿混为一谈：**

- **① `present_files` 不必每次都调用**。用户反馈"为什么每次都要执行 present_files，关键是执行这一步很耗时"（单次占用 17.13）。中间过程的验证、自检、脚本输出一律不必交付；打开 HTML 预览要渲染整页，是耗时主因。**是否需要交付、是否打开预览，以用户明确指令为准**，不要每步自动 present、也不要机械"收尾必 present"。
- **② 但"少交付"绝不等于"少确认"（用户特别纠正）**。**Gate 1 / Gate 2 / Gate 3 的确认，永远必须等用户当次、明确、点名到这一步的指令。** 不得因"减少交付"顺势理解为"可以减少确认、可以连续推进"。**"直接做 / 一次做完 / 继续做"这类概括说法，不得自行扩大解释为对未提及关卡的授权**；用户没点名的关卡照旧停手。宁可多停一次问一句，不要先斩后奏。
