## 一、密度（C24 · C25 · C26）

### C26 密度估算：直接 import 工具的 `total_of`，不手写公式 ⭐⭐
- **踩坑**：我手算 `130+80×标题行+66×正文行+23×(段数-1)` 得 **64.9%**，官方脚本报 **61.6%** ——
  **差 5%，正好横跨目标带下限 62%**，判断直接反过来。
- **真公式**（密度脚本 `total_of`，content 卡）：`32+28+head_h+40+30+body_h`，**不含 `23×(段数-1)`**。
- → **凡估算密度，一律 import `工具脚本/卡片密度预估_density.py` 的 `total_of`**；手写公式＝自己造口径（同 C22）。

### C25 密度是「行数阶梯」，可用「标题行数」配平 ⭐⭐（最实用）
```
content 卡块高 = 130 + 80×标题行数 + 66×正文总行数 + 23×(段数-1)
目标带 869~953px（62–68%）
→ 标题2行+3段+9行=930 ✅ ｜ 标题2行+4段+8行=887 ✅ ｜ 标题1行+3段+10行=939 ✅
```
- **阶梯特性**：改 1 行 = ±66px ≈ ±4.7%；**跨档就跳**（8 行=61.6% → 9 行=66.3% → 12 行=77.4%）。
- ⭐ **文案行数改不动时，改「标题行数」是配平密度的有效手段** ——
  长标题拆两行 = 块高 +80px，足以把 61.6% 抬进目标带。
- **timeline 卡同理会跳档**：5 节点必须 `tl_gap≤20`、4 节点需 `tl_gap=64`
  → 已把 `tl_gap` 做成**配置项**按卡传值（渲染器已改造）。
- ⛔ **改版式常量必须同步四处**：算高公式 + 绘制循环 + 收尾线坐标 + 预估脚本。
  （只改一处时，预估与实际差了 3%。）

### C24 先判「过密还是过稀」，再选手段 ⭐⭐
**改版式与改内容，对密度的影响方向相反** —— **行距收紧 → 同样文字占高变少 → 密度下降**。
实测：某篇旧行距 1.78 = 48.8% → 新行距 1.66 = **46.5%（更稀）**。

| 病情 | 解法 | 实例 |
|---|---|---|
| **过密**（>70%） | 压文字（**压行距也有帮助**，两者同向） | 父母做到这点（最高 93%） |
| **过稀**（<58%） | **必须补内容**（压行距只会更稀） | 孩子总犯错误 / 为什么学生不喜欢上学（30/65 张过稀） |

- ⛔ **默认"过密"就直接压行距 = 开错药**。**先量基线，再决定方向。**
- ⭐ 判断依据＝`卡片密度预估_density.py` 的统计行（目标带／偏高／偏低·过稀／破红线）。
- ⭐ **补内容先解「目标行数」，再写文案**：两系列初始都过稀，我第一次凭感觉补写，**6 张直接破红线（最高 85.8%）**。
  → **先跑密度脚本拿到目标行数区间，再按行数写**，返工数大幅下降。**不要"写完再量"。**

## 二、渲染器（C27 · C31 · C33）

### C27 渲染器 `save(limit_kb=100)` 必然贴上限 ⭐⭐
- 它取"**第一个 ≤100KB 的 q 值**"，所以永远贴着 100KB —— 实测收尾卡余量仅 **8 字节**（同 C11）。
- → 已改为 **98**（留 2KB），画质无可见差异。
- ⚠️ **各系列渲染器都是同一份代码的副本，应同步推广。**

### C31 ⛔⛔ 渲染器不得在「import 时」产生文件系统副作用
- **踩坑**：`卡片文章渲染_card_render.py` 在**模块顶层**写了 `os.makedirs(OUT)`，
  而 `OUT` 是**"第1篇"的硬编码默认值** →
  ① **任何 import（含密度预估脚本）都会凭空建出** `卡片文章/发布包_第1篇_xxx/卡片发布包/` 空目录；
  ② **跑第 2 篇时若配置未生效会错写进第 1 篇**。
- → **建目录一律移出模块顶层**，交给"配置读取完成之后"执行。
- ⚠️ **全库 7 个渲染器都有此缺陷**（同源代码副本），已产生 3 个多余空目录。
- **共性教训**：**只读的核对不该变成有副作用的操作**；产生的目录会被误当正式产物。

### C33 收尾卡金句有「宽度上限」，写前先量 ⭐⭐
- 高亮金句块**按文字宽度自适应**，**超宽就溢出画布**（实测报"越界 (-45, 580, 1287, 672)"）。
- **qsize=72 粗体下的实测临界值**：单行总宽 **≤1100px 安全**、1152px 已溢出。
- 换算成字数：**约 16–17 个汉字**（含标点）。
- → **写收尾金句前先 `draw.textlength()` 量宽度**；超了就**压缩表述**
  （如"还愿意往前挪一步的"→"肯往前走一步"），**不要去改版式参数**。
- ⭐ 与 C20 同源：**渲染器报警时，先查内容是否超载，再看版式。**

### C28 改配色前先 grep 色值用法 ⭐
- `GOLD` 是高亮块**底色**（块内文字用 `INK` 深色），差点填成深金 → 会"深字压深底"。
- **色值含义要看代码，不能凭变量名猜。**

## 三、核对与检测（C29 · C32 · C30）

### C29 查 data 污染必须用完整正则 ⛔
- 第一遍只 grep `data-id` 得 0，误判"没污染"；实际属性名是 **`data-page-node-id`**（117 处）。
- → **一律用 `\s*data-[a-zA-Z0-9-]+=`**，不要用想象的属性名。

### C32 描述与卡片的「重复」要分两类 ⭐
- **核心事件的原话**（如"我不聊"）在描述里保留**是必要的** —— 描述是钩子，必须交代发生了什么；
  该改的是**整句照搬**（实测抓到最长 **31 字**逐字重复）。
- → **机械匹配只作筛子，命中后逐条人工判断**（与 C22 同源）。
- **纪律**：**设计阶段就跑一次重复度检测**（不必等写完），本次靠它提前清掉 5 处。
- ⭐ 同源教训：**扩写描述时最容易犯的错，是顺手把卡片内容再讲一遍**。
  我把描述扩到 608 字，复查发现 4 段里 **3 段与收尾卡重复** → 重写为 485 字，改讲卡片没讲的。
  **SOP 的「扩写后必须重做重复度对照」正是为此** —— 务必执行，别省。

### C30 自检脚本曾漏「原创真实经历」类（已修）⭐
- `系列发布全套自检_selfcheck.py` 严格分支只认"非原文摘录"三类 →
  **真实经历类系列永远无法通过**（这类本就没有"非原文摘录"一说）。
- 已补判据：`真实经历 + (模糊化|转载请联系授权|不构成专业建议)`。
- **教训：判据要覆盖「内容类型分轨」的每一类，否则会把合规稿判成不合格。**

### C22 判据设计错了，结论就全错（复核存量时）⭐⭐
复核「儿童情绪管理」时连发 3 次误报 ——
① 用「12 字精确前缀」判"卡片照抄长文" → 全红（**卡片本就该改写压缩**，逐字匹配必然全红）；
② 判"缺引导原文"只查最后一段（实际写在第 2 段）；③ 把"**不是**永远不发火"误判为绝对化。
- → **复核前必须先想清楚"什么才算真问题"，再设计判据**；
  长句级重复要用**最长公共子串（≥14 字）**，不用前缀匹配。
- **黑名单／匹配词越短越易误报。**
- 同源：**字段表标注必须与卡面逐字一致** —— 我在字段表里"顺手统一"了标注口径，
  但卡面印的是另一种 → 不一致。**改标注要同步改配置并重渲**，否则只改字段表＝造假。
- ⭐ 反向提醒：**多类标注不必然是"过散"** —— 若各类有明确指向（心得/方法/观点/边界），
  **是合理区分，不该硬合并**。判"过散"前先问：这几类各指什么？

## 四、环境与工具踩坑（通用）

### ⛔ `.gitignore` 规则的四类真实漏网（务必按此实测）
1. **前缀必须与真实目录名逐字一致**：规则只写英文 `_backup*`，而实际目录叫**中文** `_备份_更新前_20260918`
   → **该目录一直没被忽略**（提交前才发现）。**中英文混写的近似前缀＝静默漏网。**
2. **`.` 开头的目录用 `前缀+*` 匹配不到**（`_tmp*` 匹配不了 `.tmp-npm-cache`）
   → 实测该目录 **58MB npm 缓存** 差点入库。`.` 开头须**另写规则**（`.tmp-*/`）。
3. **备份 zip 会散落在成果目录**：`_专家/xxx.backup-*.zip` 会被 `git add -A` 带进暂存区
   → 已加 `*.backup-*.zip` 忽略。**约定：备份一律归口 `_备份/<对象>/`。**
4. **反例：不可忽略的正式物** —— `_资产/技法库/_拆解报告/` 是正式成果、`_build_preview.py` 是正式工具。

- ⭐ **加规则后必须用 `git check-ignore -v <真实路径>` 实测**，别只看规则写得对不对。
- ⚠️ 改 `.gitignore` **管不到已跟踪文件** → 需 `git rm --cached` 出库。

### 其他环境坑

- **收口双句补写纪律**：陪伴块色值（如 `#EEF4F2`）**正文中间可能也在用** →
  从前往后 `re.search` 会命中中间块并造成**破坏性替换**（曾删掉第 2 篇一个内容块）。
  → **文末插入/替换一律 `rfind` 倒序定位**，并加"含'爸爸'等关键词"的安全校验。
- **判"缺不缺"先跑工具，别凭肉眼** —— 某系列 5 篇肉眼看着都像"有结尾"，实测缺 6 项。
- **Bash（Git Bash）**：需先 `export PATH="/usr/bin:/bin:/c/Windows/System32:$PATH"` 才能用 `ls/find/du`。
- **⛔ 别用 Bash heredoc 传中文路径**（反斜杠会被转成混斜杠）→ 写成 `.py` 脚本文件再执行。
- **⛔ 改 Windows 绝对路径别用 Python 字符串 `replace`**：反斜杠在 `r'...'` 字面量里转义后匹配不上
  → **改用 Edit 工具直接改那一行**，可靠得多。
- **生成 .docx**：python-docx，venv `C:\Users\ZhuanZ\.workbuddy\binaries\python\envs\default`（已装 1.2.0）。
- **大仓库推送放后台**：100MB+ 前台 `git push` 易超时被 SIGTERM，用 `run_in_background`。
